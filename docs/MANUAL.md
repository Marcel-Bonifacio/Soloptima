# Soloptima manual

Reference for each page of the app, the models behind the results, and the known limits. Sources are cited in IEEE style: a number in square brackets, in the order of first citation, with the full entry under References at the end of this document. Installing Soloptima is described below; to build it from source, see the [README](../README.md#build-from-source).

## Download and install

You do not need Rust, Node.js, Python or any other tool to use Soloptima. Each download below is the complete program: install it like any other app. The setup programs need no internet connection, and Soloptima works offline. Only the map, weather downloads (and forecasts) and the update check need the internet. Projects, simulations, the optimiser, finance and reports all run on your computer.

### Which file do I need?

| Your computer | Download this file | Notes |
|---|---|---|
| Windows 10 or 11 (64-bit) | [Soloptima-Setup-windows-x64.exe](https://github.com/Marcel-Bonifacio/Soloptima/releases/latest/download/Soloptima-Setup-windows-x64.exe) | A setup program with a few pages to click through. No administrator rights needed. |
| Mac with macOS 11 or later | [Soloptima-mac.dmg](https://github.com/Marcel-Bonifacio/Soloptima/releases/latest/download/Soloptima-mac.dmg) | One file for every Mac, Apple silicon and Intel. |
| Linux, any distribution (x86_64) | [Soloptima-linux-x86_64.AppImage](https://github.com/Marcel-Bonifacio/Soloptima/releases/latest/download/Soloptima-linux-x86_64.AppImage) | Runs without installing and updates itself. |
| Ubuntu or Debian (x86_64) | [Soloptima-linux-x86_64.deb](https://github.com/Marcel-Bonifacio/Soloptima/releases/latest/download/Soloptima-linux-x86_64.deb) | Installs like other Ubuntu software. Soloptima does not update this copy itself. |

For a computer without internet, download the file on another computer and copy it over, for example on a USB stick.

The builds are not code-signed yet, so Windows and macOS show a security warning the first time. The steps below say what to click; [Signing](../README.md#signing) in the README explains how signed builds are made.

### Windows

1. Double-click `Soloptima-Setup-windows-x64.exe`.
2. If Windows shows **Windows protected your PC**, select **More info**, then **Run anyway**.
3. The setup program opens on a welcome page. Select **Next**.
4. Read the licence (Apache License 2.0), tick **I accept the terms of the licence agreement** and select **Next**.
5. Keep the suggested folder and select **Install**. Soloptima installs for your user account only, in `%LOCALAPPDATA%\Programs\Soloptima`, and adds a Start menu shortcut.
6. Leave **Start Soloptima** ticked and select **Finish**.

Soloptima's window uses the Microsoft Edge WebView2 Runtime. Windows 11 and current Windows 10 already have it; if it is missing, the setup program installs the copy it carries, without a download.

Uninstall from **Settings > Apps**; your profiles and projects stay in place.

### macOS

1. Double-click `Soloptima-mac.dmg`. A window opens with Soloptima and the Applications folder.
2. Drag Soloptima onto Applications.
3. The first time only: open Applications, right-click Soloptima (or Control-click), select **Open**, then confirm with **Open**. A plain double-click is blocked once because the app is not notarised by Apple yet. On macOS 15 and later, if no Open button appears, go to System Settings > Privacy & Security and select **Open Anyway**.
4. After that, start Soloptima like any other app. Close the window or press Cmd+Q to quit; your work is saved first.

Starting Soloptima while it is already running brings its window to the front.

### Linux

AppImage:
1. Make the file executable: right-click it, open **Properties > Permissions** and tick **Allow executing file as program** (or run `chmod +x Soloptima-linux-x86_64.AppImage`).
2. Double-click it.
3. The AppImage carries its own FUSE library, so `libfuse2` is not needed, but the system must support FUSE, as almost every desktop does. If it still does not start and mentions FUSE, run it from a terminal with `./Soloptima-linux-x86_64.AppImage --appimage-extract-and-run`, or install FUSE (`sudo apt install fuse3`).

Debian and Ubuntu package: run `sudo apt install ./Soloptima-linux-x86_64.deb` in the folder that holds the file. It needs `libwebkit2gtk-4.1-0` and `libgtk-3-0`, which apt installs when they are missing; that takes a connection to your package source, so on a computer without internet the AppImage is the simpler choice. Soloptima does not update a .deb copy: install the next .deb over it.

### First start

The first time Soloptima opens:
1. It lists the licence (Apache License 2.0) and the terms of use, each with its own tick box. Select the **licence** or **terms of use** link to open the text in a pop-up; its box unlocks once you have scrolled the pop-up to the end. Tick both and select **Accept and continue**.
2. Create your profile: your name, and if you like your organisation and email. Select **Create profile and continue**.

There is no online account, password or sign-up: the profile is kept on your computer and keeps your projects apart from those of other people who use it.

## Profiles and the landing page

The app opens on a sign-in page. Choose a local profile or create one. A new profile first accepts the licence (`LICENSE`, Apache 2.0) and the terms of use, each read to its end in a pop-up and ticked, then enters its name; both texts are files installed with the app, so this works offline. Every profile is asked again when `TERMS.md` gets a new version. Profiles have no password: projects are plain files in the data folder, so a password would protect nothing. After signing in, the landing page lets you:
- browse saved projects, with search, sort and result badges;
- start a new project from a template, open the example study, or import a `.json`;
- switch, add or remove profiles and sign out from the profile menu (top right);
- open **Settings** from the same menu to change your name, picture, organisation and email, move the projects folder, or clear the cache.

## Where projects are saved

Projects are saved automatically:

| System | Where projects are stored |
|---|---|
| macOS | `~/Library/Application Support/Soloptima/` |
| Windows | `%LOCALAPPDATA%\Soloptima\` |
| Linux | `$XDG_DATA_HOME/Soloptima/` (default `~/.local/share/Soloptima/`) |

A `data/users/` folder next to the program or in the working directory takes precedence, which gives a portable install (e.g. on a USB stick). A folder chosen in *Settings* takes precedence over both; the choice is kept in `Soloptima-settings.json` beside the default folder (so deleting that folder later does not lose it). `--data /path/to/folder` overrides all of these for one run. A folder saved under the old name (`SolarHybrid`) is renamed to `Soloptima` on first start. The user menu (top right) shows the folder in use.

*Settings* can move the data (profiles, projects and bug reports) to another folder: everything is copied, the copy is checked, and the previous folder is left unchanged as a backup. It can also open a folder that already holds Soloptima data, such as a backup or a folder synced from another computer. *Clear cache* drops what the engine keeps in memory (downloaded weather years and PV yield checks, finished optimisation and variability runs), the satellite images of the report, and temporary files left by an interrupted save; profiles, projects and reports are not touched.

## Bug reports and feedback

**Report** in the top bar opens a form for a bug, feedback or a feature request (title, what happened, steps to reproduce, expected result, severity). It can attach the errors of the session and the open project's inputs. Every report also carries a diagnostic log, unless you untick it: the last 300 steps of the session (pages opened, buttons clicked, fields changed with their new values, every engine call with its time and how it ended, console warnings and errors), the computer (app version, system, screen and window, language, time zone, memory) and an outline of the open project (data lengths, sizes, strategy, which results exist and whether they are from other inputs). The log is kept in memory only and holds no API keys; it goes into the report's .json file in full and its last 80 entries into the .md copy. *Copy for an issue* leaves out the data folder, the project outline and the values typed into fields. Errors are also captured automatically, each with the same log: script exceptions, an engine that does not answer, and engine responses that are not its own worded messages (panics of the engine, failures of the data folder, parse errors). Messages that explain a wrong input are only kept in the session's error list. The same error at the same place is counted on one report instead of filed again, and a recurrence of an error marked fixed or closed reopens it.

Every report keeps a dated history: who reported it, status and severity changes, notes, recurrences, and when it was opened as an issue. *Bug reports and feedback* in the profile menu (or the footer) lists them and edits status, severity and notes. They are files in the `reports` folder of the data folder:
- `SOL-nnnn.json`: the report and its history (and the attached project, if any);
- `SOL-nnnn.md`: the same as a readable document, rewritten on every change;
- `README.md`: an index of all reports.

Nothing is sent anywhere. *Download .md* saves one report; *Copy for an issue* copies it without the reporter, the project and the notes; with a GitHub repository entered under the list, *Open GitHub issue* opens a prefilled issue in the default browser for you to check and submit. If the engine has stopped, captured errors wait in the window's storage and are filed on the next start.

## The application window and updates

Soloptima is a desktop application: a Tauri shell (`src-tauri/`) shows the interface in the system's web engine and links the engine (`engine/`) into the same program; the interface calls it through Tauri commands (docs/ipc.md). The shell adds what a browser tab would lack: exports open the system's Save dialog, the report prints through the system print panel, links to other sites open in the default browser, and closing the window saves the open project first.

Updates come from the GitHub releases of the project (`src-tauri/src/update.rs`, the Tauri updater, and `ui/src/screens/UpdateDialog.svelte`). After sign-in, at most once a day, Soloptima reads the latest release's `latest.json`; a newer version shows **Update to x.y.z** in the top bar with the release notes. Only when the user confirms does it download the update for the system (`Soloptima-mac.app.tar.gz`, `Soloptima-Update-windows-x64.exe` or `Soloptima-linux-x86_64.AppImage`; the Windows update file is the setup program without the WebView2 Runtime installer that the download for new installs carries, since a computer that updates already has WebView2). The download must carry a minisign signature by a Soloptima release key whose signed comment names the announced version; otherwise it is discarded and nothing changes. The app then saves and installs: on Windows the setup program installs over the old version and starts it; on macOS the app replaces its bundle and starts again; on Linux the AppImage replaces its own file and starts again. A copy that cannot replace itself (the .deb, a build from source) opens the release page instead. **Settings > Updates** turns the daily check off.

## Privacy and the local engine

There is no local server: the engine runs inside the application. The site location leaves the computer only for weather data and forecasts (PVGIS, NASA POWER, Open-Meteo, MET Norway), the PVGIS yield reference, map tiles, the report's satellite image (Esri World Imagery), the Google Maps view, place search / address lookup (OpenStreetMap Nominatim) and, when you click *OSM buildings* or Ctrl+click a roof, building outlines (OpenStreetMap Overpass); the time zone is looked up offline. The update check and an update download reach GitHub and carry only the Soloptima version. Only the interface's own window may call the engine (Tauri capability `default`, local pages only); other programs and websites have no way in.

Data folders opened in Settings may come from other computers, so Soloptima does not follow links inside them, and profile and project ids from their files must match their folder and file names.

On macOS and Linux the files Soloptima writes, and the folders it creates, are readable by your account only; folders that already existed keep their permissions.

## Models

### Solar resource and PV yield (`engine/src/pv/`, `engine/src/weather/`)
- Weather in UTC is shifted to local standard time by the UTC offset in Site. Irradiance timestamps use the source's own offset (PVGIS reports it; NASA POWER is hour-averaged).
  - Choosing a site sets the offset to the standard offset of its time zone, looked up offline from the coordinates (tz-lookup). The lookup is approximate within a few kilometres of a zone border, so the site info names the zone. A typed offset is kept while the site stays in the same zone. A project saved before the lookup keeps its offset, with a warning when it differs from the zone's.
  - Zones with daylight saving use their lower offset. Clock-time logger data is converted on import with the time basis *Local clock time with daylight saving*.
  - Half-hour and quarter-hour offsets (India +5:30, Nepal +5:45) are applied exactly. With offset n + f, local hour L = f × UTC hour (L − n − 1) + (1 − f) × UTC hour (L − n), the mean over the local hour, for irradiance, PV output, cell temperature, wind and the auxiliary load. The day-ahead schedule averages the local-time load over each forecast hour in UTC. Earlier builds rounded the offset to whole hours, which put PV 30 minutes off the load at such sites.
- NASA POWER marks missing hours with -999. Gaps of up to 3 h are interpolated linearly; longer gaps take the same hour of the previous day. A year with a gap over 72 h is refused: NASA POWER publishes its hourly irradiance about three months late, so the current year and, until May, the previous one are incomplete. The weather keeps the hours filled and the longest gap, with the service called and the download time.
- Sun position: Spencer [3] and NOAA equations. Beam/diffuse split kept consistent with GHI. Weather with GHI only is split by DISC [4] (the beam from the clearness index and the air mass at the site's air pressure), Erbs [5] or Boland-Ridley [6] (diffuse fraction from the clearness index). New projects use DISC; projects saved before it keep Erbs. On the example study, with the PVGIS beam and diffuse removed, DISC comes within 0.1 % of the yield from the full data and Erbs 0.3 % above it.
- Clear sky (PV forecaster, spectral correction): Ineichen-Perez [7] at the site elevation with the Linke turbidity, typed or estimated for each month from the weather year (the 5th percentile of the turbidity that reproduces the GHI of the hours with the sun above 17.5°, within 2-8), with its own beam and diffuse split; or Haurwitz [8] (sun height only). New projects use Ineichen-Perez; projects saved before it keep Haurwitz. The timing test of the data checks keeps Haurwitz.
- *Irradiance scale* (PV losses, 1 by default) multiplies the GHI and its diffuse part of the weather before the beam and diffuse split and the transposition, so the plane-of-array irradiance scales almost in proportion while the cell temperature, low-light loss, IAM and clipping answer to it as they would to brighter or duller weather. It is scaled there rather than on the PV output because a plain factor on the output would miss clipping and temperature; at 0.9 the example's yield falls by about 10 %, not exactly 10 %. The clear-sky reference of the forecasts is not scaled. *Wind speed scale* (wind turbines) multiplies the measured wind speed before the height correction and the power curve, so the turbine output changes by much more than the factor below rated speed and not at all above it. Both are there for sensitivity: the tornado, the optimiser's sensitivity cases and the two-way map.
- Transposition: Perez [9] with the all-sites composite coefficients: isotropic, circumsolar and horizon-band sky diffuse, sized each hour from the sky clearness and brightness (relative air mass of Kasten and Young [10]); or Hay-Davies [11] (circumsolar and isotropic sky). Ground reflection with the albedo. New projects use Perez; projects saved before it keep Hay-Davies. On the example study (7° N, PVGIS TMY) Perez adds 0.5 % to the yield at 10° tilt, 1.0 % at 25° and 2.4 % on a single-axis tracker.
- Terrain horizon: elevations at equal azimuth steps from north, clockwise (*Horizon from PVGIS* fills 48 values from the PVGIS elevation model). Beam and circumsolar light count only for the part of each hour (10 instants) with the sun above the horizon; the isotropic sky and the horizon band take the share the terrain leaves in view of the module plane (and of the back of bifacial modules). PVGIS weather has its beam blocked by PVGIS's own horizon already, so by default only the sky reduction applies to it; weather measured at the site is left as it is. Loss step *After terrain horizon*. A 10° horizon all round costs 1.5 % on the example study.
- Nearby objects (near shading): buildings (footprint and height) and trees (crown diameter and height, a column that passes the share of the beam typed for its leaves, all year for an evergreen tree, and for a deciduous one between that and 60 % for bare branches by the month's leaf cover, leaves out in April and down in October, six months on south of the equator; the sky diffuse behind a crown takes its mean over the year) placed on the layout map. Points spread over the tables (about 20 000 in all, at least one per table; a grid over the PV areas when they have no tables) at their height, from the surface height of their PV area (a roof), the table centre height and the slant, each see a near horizon: the elevation of the highest object edge at every 2° of azimuth, from rays every 0.5° and to every object corner; objects that stay below 2° are left out. The near horizons of the last two layouts are kept, so the P50/P90 years compute them once. Within each of the 10 instants of an hour with the sun above the terrain horizon, beam and circumsolar light are lost on the share of the points that see the sun behind an object (with *Electrical effect of their shadows*: bypass diodes per module substring, where each substring carries the current of its most shaded point and the inverter picks the string current that gives most power; the string current of the most shaded module; the linear loss plus a share of that string effect; or linear, the default of projects saved before; strings run along the tables, one per module up the table, three substrings per module; with the electrical model or translucent crowns the light comes from a table by sun position, 2° of azimuth by 1° of elevation, and month); the isotropic sky and the horizon band take the share the objects and the terrain together leave in view of the plane, averaged over 48 of the points. Ground-reflected light and the rear side of bifacial modules are left as they are. Loss step *After shading by nearby objects*. For each table the share of its beam the objects hide over the year (beam on the plane after the terrain horizon, by sun position) colours the layout, and tables shaded over a chosen share can be left out of the fill. A project without objects gives the same results as before. On the example study two buildings (12 m and 8 m high) and three trees (12-14 m) 15 to 40 m from the edge of a 4.4 MWp array cost 0.2 % of the yield; at 7° N the sun stands high, so the same objects cost more at higher latitudes.
  - *Tracker can stop at a local maximum* (with bypass diodes, off by default). The substrings of a partly shaded string give it a stepped power curve over the string voltage, with a peak on each step. Without the option the tracker takes the highest peak. With it, the tracker starts at the full string voltage (every substring carrying current) and moves to lower voltage only while the power rises, as a perturb and observe tracker does, so it can stay on a lower peak [45]. It never gives more than the highest peak. It is a cautious check: many inverters scan the whole curve from time to time and find the highest peak. The point does not depend on the hour before, so the light table by sun position still holds. Row shading with bypass-diode blocks has no power curve to search (it is a closed form of the shaded share [12]), so the option acts only on the shading by buildings and trees.
- PV areas with their own orientation: fixed tables of a PV area can take their own tilt and azimuth (roof faces, areas turned to their longest side) or stand east-west in back-to-back pairs. Each orientation runs the hourly model to the DC energy with the project's other inputs (GCR, table width and height), weighted by its share of the tables (of the areas' plan area when the layout has no tables; east-west half each way), and the inverters convert the sum, so clipping follows the combined profile. The PVGIS cross-check keeps the project's single orientation without objects. On the example study east-west tables at 10° give 2.2 % less energy per kWp than the south-facing tables but cut the curtailed PV energy from 0.81 % to 0.32 %; at its DC/AC ratio of 1.1 the inverters do not clip, so the yield equals the mean of the two orientations run apart (above that ratio the shared inverters clip less than two separate ones would). A canopy area (orientation *Canopy*) is one plane: its tables touch across the rows, nothing stands in front of a table, and its hourly model runs without row shading or diffuse row shading. Its rear side gets light only with edge rows on: then the back of a bifacial canopy sees the ground as one open row as wide as the canopy (its tables, or its area, across the way they face) at the table centre height, mostly its own shadow under it, so the gain rises with the height (on 25° tables 13.7 m wide with 70 % bifaciality, 4.8 % at 3 m and 6.4 % at 6 m). On the example study at 30° and GCR 0.6 with diffuse row shading on, a canopy yields 3.3 % more per kWp than the same area as ground rows and holds 1.8 times the capacity.
- Row shading: 2-D infinite-row beam shading from GCR and profile angle; trackers with backtracking (no beam shading) or true tracking (shading). With bypass-diode blocks (new projects; projects saved before keep the linear loss) every block the shadow touches stops contributing beam light: beam factor (1 − F)(1 − N_shaded/(N_blocks + 1)) [12], with 2 blocks per portrait module (half-cut cells) and 3 per landscape module up the table unless typed.
- Trackers on slopes: axis tilt and ground slope across the rows. The rotation follows the sun projected on the plane across the axis, backtracking turns the rows so they just clear each other on the slope (slope-aware backtracking, Anderson and Mikofski [13]), and the module plane follows from the rotation [14].
- Diffuse row shading (on for new projects, off in projects saved before it): 2-D view factors of a row in an infinite array of identical rows [15]. The circumsolar light is shaded with the beam; the isotropic and horizon parts take the view factor of the sky above the row in front, averaged over the slant in closed form; the ground-reflected light comes from the ground between the rows, in 30 strips per pitch, each lit by the beam outside the rows' shadows and by the sky through the gaps between the rows, and seen by its own view factor. The table width up the slope is the modules across a table times the module side (Layout page), the height of the table centre or tracker axis is a Mounting input. On the example study (10°, GCR 0.45) it costs 0.3 % of the yield, at 25° 1.3 %, on a tracker at GCR 0.35 1.4 %.
- Bifacial modules: the back of the row receives the light reflected by the ground strips (by their view factors from 12 points of the slant, so the share of ground in the row's own shadow falls as the table is mounted higher), the sky above the row behind and, when the sun is behind the modules, beam and circumsolar light outside the shadow of the row behind. With the diffuse IAM, times the bifaciality and (1 − rear-side loss for structure shading and mismatch), it adds to the front's effective irradiance before the low-irradiance, temperature and electrical losses, and it heats the cells. The loss chain shows it as *Effective incl. bifacial rear side*. On the example study, PERC modules (bifaciality 70 %) add 4.4 % at 1.5 m (3.3 % at 1.0 m, 5.8 % at 2.5 m); a 1P tracker with 80 % at 2 m adds 7.1 %.
- Edge rows (*First and last rows see more sky and ground*, on for new projects): the first row of an array has no row in front of it and the last row none behind it. A table with no table 0.25 to 1.5 pitches ahead of it (and less than half a table aside) keeps its whole beam and, with diffuse row shading, the sky of its plane and the light reflected by the open ground in front of it; the back of a table with none behind it sees the open sky and ground behind and the beam from behind without a row's shadow. The open ground is the ground view of a row with rows on one side only (2-D, 10 strips per pitch over 12 or more pitches each way, each with its own sky view and the shadows of the rows that stand). Each orientation of the array counts its tables at the front and back edge on the layout map (trackers, whose front turns from east to west, the mean of both); without tables the *Number of rows* puts one row of them at each edge. Front and back quantities are weighted by these shares before the rest of the chain. East-west pairs have no edge rows; a canopy is one open row (below). On 25° bifacial rows (70 %) at GCR 0.5 a single row yields 3.3 % more than an interior row, two rows 1.7 % and ten rows 0.3 %.
- Sloped ground: a PV area of fixed rows can stand on ground with a slope (0-45°) falling towards an azimuth (by default the way its tables face). The tables keep their tilt and azimuth; the ground coverage ratio counts along the ground, so the fill sets the rows closer on the map by the cosine of the slope across the rows. Only the slope across the rows matters for infinite rows: the row in front stands lower when the ground falls towards the front, so the beam shading takes the profile angle from the ground (sin(ap + slope) / sin(ap + tilt)); the view factors of the rows, of the ground between them and of the edge rows take the tilt from the ground, the ground takes the beam at its own angle of incidence, and the beam shading on the rear side counts from the ground too. Near shading takes the area as level. On 25° rows at GCR 0.6 and 35° N, a 10° slope towards the south yields 0.2 % more than level ground (monofacial, beam shading), one towards the north 2.4 % less; bifacial rows with diffuse row shading gain 1.2 % and lose 2.8 %.
- Optical: ASHRAE IAM (b0, all diffuse light at 59°), Martin-Ruiz [16] (a_r, the model of IEC 61853-3 [17]) or the physical glass model (Fresnel reflection with an optional antireflective coating, absorption in the glass) [18]. With the last two the circumsolar light counts as beam and the sky and ground diffuse light take the IAM integrated over the sky and ground in view of the plane [19]. New projects use Martin-Ruiz, which gives 0.6 % more yield than ASHRAE with b0 = 0.05 on the example study; projects saved before keep ASHRAE. Soiling and albedo as one annual value or 12 monthly values by local month.
- Spectrum (optional, by cell type): PVSPEC mismatch factor M = a·kc^b·AMa^c [20] from the clear-sky index and the absolute air mass, step *After spectral correction*. On the example study mono-Si gains 0.3 %, CdTe 2.3 %.
- Snow: monthly loss of Townsend and Powers [21] from the snowfall, snow days and humidity of each month and the month before, the tilt, the slant height and the clearance of the lower edge, with the string factor of Townsend and Previtali [22]; trackers count at their largest rotation. Relative humidity in the weather (`weather.rh`, %) gives the monthly loss the mean humidity of each month in place of the typed value. With hourly snowfall in the weather (`weather.snow`, cm per hour) the hourly cover model of Marion et al. [23] runs instead: a fall over 1 cm/h covers the modules, which shed 19.7 % × sin(tilt) of their slant height per hour while the air temperature in °C is above −POA/80 (POA in W/m²); a string stops while any of its modules is covered. Step *After snow cover*. Snowfall and humidity come with the weather: *Fetch* asks NASA POWER for both (snowfall over land, PRECSNOLAND, in mm of water per hour, taken as as many cm of fresh snow; RH2M) and keeps the snowfall only for a year with snow, and the PVGIS typical year gives the humidity; a CSV can carry both columns (snowfall in cm or mm of snow, or mm of water, per interval; humidity in % or as a fraction). Multi-year weather runs use neither.
- Thermal: heat-loss factor model `Tc = Ta + α·G·(1−η)/(Uc + Uv·v)`, or NOCT `Tc = Ta + (NOCT − 20)/800·G`; G includes the bifaciality times the rear-side irradiance.
- Cooling of the modules (PV page) sets Uc for the common mountings: 29 W/m²K for an open rack or a canopy with an open back, 20 for modules flush on a roof or under a canopy with a closed back, 15 for roof-integrated modules; Uv stays 0. Typing Uc or Uv turns the choice to Custom. On the example study, flush gives 2.7 % and roof-integrated 5.7 % less yield than an open rack.
- Electrical: low-irradiance loss, temperature coefficient, mismatch / wiring / LID / quality, inverter efficiency, clipping at DC/AC ratio, AC/transformer losses, availability, annual degradation. The inverter takes the weighted efficiency every hour, or (new projects) a part-load curve with losses k0 + k2·p² of the AC rating at output p [24], fitted to the peak efficiency 1/(1 + 2√(k0·k2)) and the European weighted efficiency; sunny sites run mostly near rating, so it gives 0-0.5 % more. Degradation is linear, 1 − d·(y − 1), as module warranties (new projects), or compound, (1 − d)^(y − 1); Project finance scales its contract energy the same way. The inverter's AC rating does not degrade with the modules, so in later years the dispatch takes back part of the energy clipped in year 1: an hour gives min(f·(p + x), c) per kWp for year-1 output p, clipped energy x, degradation factor f and AC limit c. Earlier versions scaled the clipped output too, which understated late-year PV at a high DC/AC ratio.
- MPP tracking loss (PV losses, 0 % by default): the share of the array's DC power the inverter's tracking misses, taken off after the mismatch, wiring, LID and quality losses and before the inverter efficiency, as step *After MPP tracking*. EArray in the monthly balances stays the array's output before it. Lab tests of one tracker under fluctuating irradiance reported dynamic tracking efficiencies of 94 to 99 % [46]. Those irradiance steps are much faster than most real hours, so the 1 to 6 % they imply is probably best read as an upper bound, not as an annual loss; 0.5 to 1 % may be a fair cautious value for a modern inverter. At 0 % the results are those of earlier versions to the byte.
- Wind turbines: the 10 m wind scaled to hub height by the power law, then the power curve, which holds for standard air (1.225 kg/m³). The speed is read as v·(ρ/1.225)^(1/3) [25] with ρ from the standard pressure at the site elevation and the hourly ambient temperature, so a hot or high site gets less below rated wind.
- DC wiring loss: a constant fraction of every hour (annual basis), or the loss at STC power as yield reports usually state it, scaled each hour with the string current and inversely with the string voltage, both relative to STC (I²R loss). A 1.5 % loss at STC then costs 0.8 % of the annual energy on the example site; sunnier sites lose more.
- Monthly balances: GlobHor, DiffHor, T_amb, GlobInc (module plane before shading), GlobEff (front side after shading, IAM and soiling), EArray (DC), E_avail and PR for every month and the year. The normalised production per kWp and day splits the reference yield into the final yield Yf, the system losses Ls and the array capture losses Lc; after a simulation it adds the unused (curtailed) PV energy Lu and the PR of the PV energy delivered.
- PVGIS cross-check: after every yield calculation the yield is compared with PVGIS PVcalc for 1 kWp of free-standing crystalline silicon (trackers: PVGIS's single inclined axis at 0°, so north-south axes only). The comparable Soloptima yield leaves out row shading, the rear side of bifacial modules and inverter clipping, which PVGIS does not model (trackers also track without backtracking or a rotation limit), and the losses PVGIS does not model itself (soiling, monthly soiling as weighted by the irradiance of each month, mismatch, wiring, LID, quality, inverter, AC, availability) become its system loss. A gap of more than 8 % is flagged. PVGIS uses its own thermal and spectral models and the multi-year average of its radiation database, so a few percent is normal; with weather from another source or a single PVGIS year the comparison is not like for like. On the example site PVGIS gives 1,323 kWh/kWp and Soloptima 1,356 kWh/kWp (+2.5 %). PVGIS is asked again only when the site or orientation changes; offline the check is skipped.

### Measured load and weather files, data checks (`engine/src/series/`, `ui/src/lib/tsimport.svelte.js`)
*Upload CSV* on Solar resource and Load opens an import dialog. It shows the first 20 lines and guesses the time column, the value columns and the units from the header; you confirm or change them, with the date order, the year, the time basis and the moment of the interval the stamps mark. The engine then reads the whole file and reports what it found before the data replace the project's:
- Delimiter: semicolon, tab or comma, whichever splits most of the first 20 lines evenly, so title or metadata lines above the data (as in PVGIS downloads) do not decide it.
- Timestamps: ISO 8601 (a stamp with Z or +hh:mm uses its own offset), dates with -, / or . in any order (detected from a day above 12; a file in which no day is above 12 must be told), PVGIS stamps and Excel serial days, with the time of day in the same or its own column. Stamps are converted to UTC with calendar arithmetic, without operating-system time-zone calls. Local clock time with daylight saving uses the clock changes of the site's time zone, found to the minute by the browser; the hour repeated in autumn takes the standard offset on its second occurrence.
- Rows are sorted, and duplicate stamps averaged and counted. The interval is the most common step; another step on more than 5 % of the rows is reported with its dates.
- Units: mean power (kW, W, MW) or energy per interval (kWh, MWh) divided by the interval; irradiance in W/m², or Wh/m², kWh/m² or MJ/m² per interval; temperature in °C or K; wind in m/s or km/h.
- Each sample covers its interval as labelled (start, end, or centred on an instantaneous sample), and each hour is the time-weighted mean of the samples that overlap it: in local standard time for load, on the file's own basis for weather. An hour less than half covered is missing. Hourly instantaneous samples thus become the mean of the stamps at the start and the end of the hour.
- The year with most data is taken (or a chosen year, or for load the last 12 months, each day at its calendar date), without 29 February.
- Gaps: weather as for NASA POWER (up to 3 h interpolated, longer gaps from the previous day, over 72 h refused); load up to 3 h interpolated, longer gaps from the same hour a week earlier (a week later at the start), over 72 h refused unless *Fill long gaps from adjacent weeks* is chosen. Zeros are data, never gaps.
- The report gives the rows read and not read, duplicates, rows out of order, the interval, the period, the coverage, the missing and filled hours and the longest gap. One hour missing in spring and one doubled in autumn in a file read as standard time point to clock time with daylight saving. Unit hints compare the load peak with the genset fleet and the annual GHI with 700–2,700 kWh/m².
- Without a time column every row is one interval in file order from 1 January, as before, from the columns chosen in the dialog (the load upload used to take the last number of each row). The file must hold one year of hourly, half-hourly or quarter-hourly rows; a row without a number is an error naming its line, and a missing weather cell is a gap instead of 0 W/m², 25 °C or 1 m/s. Headless project JSON takes the same lengths (8760, 17520 or 35040 values; 8784, 17568 or 35136 in a leap year).

After every weather download or upload and every load upload, the *Data checks* under the annual summary and the load statistics list flags by hour. They are kept with the project and change nothing:
- Weather, on the file's own time base with the sun at the start, middle and end of each hour: GHI above 5 W/m² with the sun more than 2° below the horizon; zero GHI with the sun above 15°; GHI above 1.5 E0 μ^1.2 + 100 W/m² or DHI above 0.95 E0 μ^1.2 + 50 W/m² (μ: cosine of the zenith angle, E0: extraterrestrial irradiance; the physically possible limits of the BSRN tests [26], which on hourly means catch only gross errors); DHI above 1.05 GHI + 10 W/m²; GHI differing from DNI × cos(zenith) + DHI by more than 8 % (sun above 15°) or 15 % (lower sun), and beam on a horizontal plane above GHI (the comparison tests in [26]); a non-zero value stuck for 4 daylight hours (GHI) or 6 hours (temperature, wind); the same value at the same hour on 3 days or more (daylight GHI, temperature); temperature outside -40 to 60 °C or a step above 10 °C in an hour; wind below 0 or above 40 m/s; a missing temperature or wind column; annual GHI outside 700–2,700 kWh/m².
- Timing: over 24 h centred on each day's solar noon on the file's time base, the centroid of the irradiance of each clear day is compared with that of the Haurwitz clear-sky model averaged over the hour as the PV model times it. Clear days have a daily clearness of at least 0.9 × the 90th percentile of their month and a variability of at most 1.5 times the clear sky's. The median offset gives the verdict: within 10 min the stamps match the sun; 20–40 min means instantaneous samples read as hour means, or the reverse; whole hours (within 10 min per hour) mean interval-end stamps read as interval-start, or a clock error; about the UTC offset means a wrong UTC flag; monthly medians 40–80 min apart point to a clock change during the year; with fewer than 10 clear days there is no verdict. *Shift 1 h earlier* (or later), *Treat as instantaneous samples* and *Timestamps are UTC / local time* change the weather only when clicked. On the example study, the 133 clear days of the PVGIS TMY peak 10 min before the clear-sky model.
- Load: near-zero runs (below 2 % of the 95th percentile for 2 h or more); a value stuck for 6 h or more while the rest of its day varies by more than 1 % of its mean, so flat process loads pass; linear infill (4 or more equal non-zero steps, which also marks a 3 h gap filled by the import); spikes above the median + 6 × 1.4826 MAD of the same hour of the week in the 8 weeks around it, so a level shift or a season is not a spike; level shifts of the daily mean by binary segmentation of its logarithm (at most 5, each a step of 10 % or more between segments of at least 30 days, with a BIC penalty); a peak above the genset fleet or below a fifth of one unit, with the unit error that would explain it (W, MW, kWh per 15 or 30 min). There is no clock check on load: a flat 24-hour load gives no timing signal.
- The score is the share of days without a flag. Flagged days are outlined in the heatmaps. The report has a *Data quality* paragraph and table under the resource and the load, and the workbook a *Data quality* sheet with the flagged hours (the first 200 of each data set).

### Load from an appliance list (`ui/src/lib/appliances.js`)
The *Appliance list* card on the Load page builds the load from what is used, for a village or a building with no records. Each row is an appliance: its power (W), how many there are, the hours a day it runs in each of four seasons (Dec–Feb, Mar–May, Jun–Aug, Sep–Nov) and the hour it starts. It runs from the start hour for that many hours, the last hour in part (2.5 h from 23:00 is full power at 23:00 and 00:00 and half at 01:00), so it stays in its window and its energy a day is power × quantity × hours. The rows are added up and multiplied by the number of households. That gives an average day for each season, which every month of the season takes in place of the daily shape and the monthly scaling. The weekend load, the day-to-day and hour-to-hour variability and the scale to an average load then apply as for a daily shape, so the result is the same kind of 8760-hour `load.kw` series and the engine sees nothing new.

An edit that leaves energy in the list sets the daily shape template to *Appliance list* and generates the profile; with the list empty the daily shape is used again. The card shows the energy a day and the highest hour of the average day of each season. The list is saved in the project (`load.appliances`) and stays editable; it never goes to the engine.

### Measured PV output against the model (`engine/src/pv/reconcile.rs`, `ui/src/lib/pvmeter.svelte.js`)
For an existing plant, *Upload meter CSV* on the *Measured output against the model* card of the PV & wind page reads the metered AC output with the import dialog of the load (kind `pv`): timestamps in any time basis, any interval up to an hour, mean power (kW, W, MW) or energy per interval (kWh, MWh), several columns summed. The hours are turned into local standard time as the load is, which is the time base of the yield model. Nothing is filled: hours the file does not cover stay empty, and only the hours present in both the file and the model are compared, so a part of a year is enough. Small negative values (the inverters' own use at night, down to -2 % of the peak) become 0; larger ones are refused. The meter is kept with the project (P.pv_meter, about 70 kB for a year), saved, exported and imported with it like the measured load, and is not an engine input: it changes no result and no fingerprint of a result until a fitted value is applied.

After every yield calculation the engine compares the meter with the modelled AC output (kWp × the hourly output per kWp, year 1, before any curtailment by the dispatch):
- Daylight hours are the hours with output in the model or at the meter. An hour with GHI of at least 200 W/m² and the meter at or below 1 % of the model is a probable outage. Partial outages (one inverter of several) are not detected.
- Statistics, as model − meter: MBE (mean, in kW and as a share of the mean metered output), RMSE (in kW and normalised to the mean metered output) and R² = 1 − Σ(model − meter)² ÷ Σ(meter − mean)², which falls with bias as well as with scatter. They are given over the running hours (daylight, outages left out) and over all daylight hours. Monthly: hours compared, outage hours, metered and modelled energy and the deviation model ÷ meter − 1.
- Fit: the model is taken back to a clean, always available plant (÷ (1 − soiling) ÷ availability of the project, month by month). The soiling is 1 − k, k the least-squares factor of the meter on the clean model over the running hours, kept within 0 and 30 %; a month with at least 30 running hours also gets its own. The availability is 1 − the share of the clean model's energy that falls in the outage hours. Applied together, the model's energy over the hours compared matches the meter's. The statistics of the model with the fitted values (constant and monthly soiling) over all daylight hours show the change in RMSE.
- *Apply soiling and availability* writes the fitted soiling (constant, or by month when three months or more have their own) and the availability into the PV inputs; the yield is calculated again and the comparison follows. *Undo* puts the old values back while the applied ones have not been edited. Nothing changes the project until you apply.

Soiling enters the model before the temperature, low-light and clipping steps, so the yield after Apply moves almost, not exactly, in proportion. The fitted soiling takes every steady shortfall of the plant against the model (capacity, weather source, meter position, degradation since commissioning), not only dirt, and a plant that curtails PV in a full battery or at low load shows the curtailed hours as a shortfall: use a period or a meter without curtailment, or read the soiling as a combined loss. The report shows the comparison in the PV section, and the workbook has a *PV meter* sheet. `docs/VALIDATION.md` explains how to calibrate with it.

### Inter-annual variability and P50/P90 (`engine/src/resource.rs`)
Lenders size debt on a P90 case, but in a diesel hybrid the fuel saved and the revenue do not scale with the PV yield: genset minimum loading, a full battery and take-or-pay floors damp them. The *Inter-annual variability and P50/P90* card on the Solar resource page therefore runs year 1 of the plant once with every historical weather year (PVGIS hourly series 2005–2023, or NASA POWER 2001 to the last complete year), with the sizes and settings unchanged, and gives each result its own spread:
- The spread is used only as ratios: r = value ÷ multi-year mean, and σ_iav is the sample standard deviation of r. P50 is the result with the project's own weather.
- The project weather need not be an average year. The card, the report and the *Resource years* sheet state how far its specific yield is from the multi-year mean of the weather years (P50 ÷ mean − 1), and warn above 2 %: a single NASA POWER or PVGIS year, or a CSV of one year, then makes P50 and the whole base case better or poorer than an average year, so use a TMY or a long-term average for the base case. With a TMY as the project weather, such a gap comes from a different database or period, or from the typical year's choice of months; with a single year from another database, it mixes the year and the difference between the databases. The gap does not change the P90 ÷ P50 factor, which is a ratio. The chart draws each weather year as a percentage of the multi-year mean (100 %), with P50 and the one-year P90 on the same basis.
- The systematic uncertainty σ_sys is the root-sum-square of the irradiance dataset (default 5 %), transposition and PV model (2 %), and soiling and availability (1.5 %). Each result's elasticity e = (M₊ − M₋) / (2 σ_sys M₀) comes from two more runs with the project's GHI, DNI and DHI × (1 ± σ_sys), so clipping, cell temperature, curtailment and genset minimum loading count. With wind turbines, each weather year also brings its own wind speeds, but the systematic uncertainty and the elasticity cover irradiance only, so the P90 leaves out the uncertainty of the long-term wind resource.
- σ_N = √(σ_iav² / N + (e σ_sys)²) for one year (N = 1) and a 10-year average (N = 10, independent years), and P_x = P50 × (1 − z_x σ_N) with z = 0.6745 (P75), 1.2816 (P90) and 2.3263 (P99). For fuel used, where higher is worse, P_x = P50 × (1 + z_x σ_N). The worst year of each result is reported too.
- Results: specific yield, fuel saved, renewable fraction, avoided diesel cost, year-1 revenue of Project finance (the avoided cost for a host-owned plant; tariff × billed energy, with take-or-pay and deemed energy, under a PPA) and fuel used. Every weather year keeps the contract of the P50 case: a tariff solved for a target IRR is solved once, for P50, and the contracted energy behind take-or-pay and shortfall penalties stays at its P50 value. Under a PPA or third-party ownership the revenue P-values are the P-values of the renewable energy delivered, mapped through the contract (take-or-pay floor, shortfall penalty), so they respect the take-or-pay floor as every weather year does. Deemed energy stays at its P50 value although curtailment drops in poor years, so with deemed energy they are slightly optimistic.
- *Use for debt sizing* sets the revenue haircut of Project finance to P90 ÷ P50 of the revenue, of one year (the default, as the factor applies to every year) or of a 10-year average. The Debt card shows where the value came from until it is typed over.

On the example site (PVGIS-ERA5 2005–2023) the yield varies by 4.1 % from year to year and the fuel saved changes by 0.94 % per 1 % of irradiance, so revenue P90 ÷ P50 is 0.915 for one year and 0.931 for a 10-year average. With PV of three times the average load (the test project), curtailment cuts the fuel-saved elasticity to 0.44. The weather years are downloaded in blocks (PVGIS: four years per request, three requests at a time, about a minute in all; NASA POWER: one request per year, three at a time), kept in memory for the session by site and range, and never saved in the project; only the summary is. PVGIS serves ERA5 reanalysis over most of Indonesia, so cross-check it against NASA POWER.

### Dispatch (`engine/src/sim/`)
Every hour of every project year (year 1 only, repeated, when *Simulate every project year* is off or the optimiser runs in fast mode):

1. Unit commitment: gensets online = ⌈(residual deficit + planned charging + spinning reserve − battery reserve) / unit rating⌉, at least *units always online* and at most the fleet. Battery reserve is the spare discharge power, limited to what the energy above the minimum SOC sustains for the *reserve duration* (default 1 h; 0.25–0.5 h covers a genset start).
2. Allocation: genset minimum loading (must run) → PV → battery → gensets above minimum → battery emergency reserve → unmet.
3. Charging: PV surplus → battery; unavoidable genset excess at minimum load → battery, else dumped; deliberate genset charging (cycle charging or EMS plan); with a grid connection and *Charge the battery from the grid*, grid charging from the import left after the load.
4. Fuel: part-load curve per online unit (datasheet table interpolated as L/h, or a linear curve: intercept + slope).
5. Load and PV balances close every hour to within 0.05 kW (checked by `cargo test`).

With a PV and wind ramp limit (15 and 30 minute steps), a rise beyond it is cut before step 1 and a fall beyond it is made up by the battery after step 2; see *Time step, ramps and forced outages*.

The *Energy flow* card draws year 1 as a Sankey diagram: PV, wind and the gensets (and the unmet energy) into the battery and the load, and out to curtailment, genset dump at minimum loading, battery losses, self-discharge and the auxiliaries. Battery losses = energy charged − discharged − self-discharge − change in stored energy over the year, so the battery's own balance closes; the change in stored energy is drawn when it exceeds 0.1 % of the throughput. The direct RE share is the part of the PV and wind used that goes straight to the load. The *Monthly energy supply* card adds the monthly balance: load, PV and wind direct, battery and diesel to the load, unmet, curtailment, genset dump, fuel and renewable fraction.

**Mixed genset fleet** (optional, Diesel & control page; `engine/src/sim/fleet.rs`). The Gensets card is the main group; further groups have their own units, rating, minimum loading, fuel efficiency at 25, 50, 75 and 100 % loading (blank: the main group's curve) and capex, O&M per kWh and per run-hour (blank: the Costs page values).
- Merit order: the groups are ranked by the cost of their energy at 75 % loading and year-1 prices (fuel, O&M per kWh, O&M per run-hour spread over the energy), and units are committed in that order. Committing u units means the first u units of the list, so a group runs only when every unit ranked before it is online, and the number of units online stays one number, as for a single group (EMS plan, firm commitment, starts).
- The units online share the output in proportion to their rating, all at one loading, as gensets on a common bus do. The least output is the sum of each online unit's minimum loading, and the spinning reserve is the headroom of the whole online fleet.
- Fuel is each online unit's own curve at that loading; capex, O&M and wear (overhaul interval and cost, life and replacement cost, below under Economics) are each group's. Simulation results, the report and the workbook (*Genset groups* sheet) give each group's run hours, energy, fuel, specific fuel, starts and O&M, and with wear its overhauls and replacements.
- A project without further groups gives the same results as before to the byte.

**Grid connection** (optional, Diesel & control page; `engine/src/sim/grid.rs`). In every hour the grid is up:
- Its import price (flat, or time of use by hour of the day or by month and hour, escalated each year, plus the carbon price on its emission factor) is compared with genset energy (fuel, carbon and O&M per kWh of that year) at the loading the units would run at to cover the hour's residual load, so a small residual that would run a unit near its minimum loading goes to the grid sooner. When the grid is cheaper it serves the load after PV and the battery and before the gensets; when it is dearer the gensets come first and the grid covers only what they cannot.
- Its spare import (limit − import) counts as spinning reserve, and no genset has to stay online, so a strong cheap grid runs the site without gensets.
- PV and wind that the load and the battery cannot take are exported up to the export limit; the rest is curtailed. Genset energy is not exported, and the battery charges from the grid only with the option below.
- Costs: the energy at each hour's tariff, a demand charge on the highest hourly import of each month, less the export revenue, all escalated with the grid escalation, enter the yearly cost and the NPC (`c_grid`); grid emissions enter CO₂ and the carbon cost. Grid imports are not renewable: renewable fraction = 1 − (diesel + grid import) ÷ energy served.
- Availability: always up; a daily pattern of 24 hours (scheduled load shedding); or random outages drawn from a yearly count and a mean length (up-times and lengths exponential, at least one hour, a fresh draw for each project year from the seed). While the grid is down nothing is imported or exported, the gensets with their units always online and the battery carry the load.
- The predictive EMS plans with the grid: its hour costs include the import and the export, and it knows a daily pattern ahead but not random outages (the hour in progress excepted). The day-ahead schedule plans with the grid too (year-1 prices, the daily outage pattern) and gives the import and export of each hour.
- The diesel-only baseline, the PV-only reference and every operating option keep the grid, so savings are measured against grid + diesel. Project finance takes the net grid cost as a running cost of the host, beside fuel and genset O&M, and a tariff at a discount to the avoided cost uses the cost per kWh of grid + diesel.
- *Charge the battery from the grid* (off by default). Load following and cycle charging use two rules. Before a scheduled outage (the daily pattern), for the hours a full charge takes at rated power, the battery charges from the grid to full and does not discharge, so it can carry the outage. With a time-of-use tariff, an hour is a charging hour when energy bought in it and used within the next 23 hours pays its losses and wear: round-trip efficiency × (later value − wear cost per kWh discharged) > price now. The later value of a stored kWh is the import price, or genset energy at 75 % loading when that is cheaper or the grid is planned down. In a charging hour the battery charges to full and the grid serves the load; in other hours it runs as usual. A flat tariff never pays the round trip, so there the rule acts only before scheduled outages, and random outages are not foreseen. The predictive EMS costs grid charging in its plan instead: while the grid is cheaper than the gensets it covers planned charging, and the plan sees the hourly price and the daily outage pattern. Stored energy at the end of its horizon is then valued at no more than the cheapest import of the horizon, so the plan does not buy energy only to hold it. Grid charging uses the import left after the load (the import limit holds for both), never coincides with export, and is billed at the hour's tariff; it counts in the demand charge, the grid emissions and, as grid import, against the renewable fraction (`grid_to_bess`, beside `grid_import`, which stays the import to the load).
- *Frequency reserve* (0 kW by default). While the grid is up the battery keeps this much power free in both directions, and its stored energy stays at least reserve power × duration ÷ one-way efficiency above the minimum SOC and reserve power × duration × one-way efficiency below the maximum, so it can deliver or absorb the reserve for the whole duration. All three strategies, cycle charging's setpoint and the EMS plan (power as a hard limit, the band as a cost of 10 × the value of lost load per kWh outside it) keep to this. A battery below the band, after an outage or at the start, is refilled from the grid whether or not grid charging is on. During an outage the reserve is released and the battery carries the load. A battery without the power or the energy for the reserve in a year does not offer it that year. Every year reports the hours the reserve was held (grid up, stored energy within the band, power free), the PV and wind the battery could not store because of the band (exported or curtailed instead) and the load it could not serve because of it (met by the grid, the gensets or not at all); the band costs energy, and that cost shows in fuel, grid cost and curtailment. With a *reserve price* per kW and year the reserve earns price × power × the share of the year it was held, escalated with the grid prices and taken off the yearly cost and the NPC (`c_fr`). Off grid nothing changes: there the battery's spare power already counts as spinning reserve.
- Results show grid import and export in the comparison table, the energy supply and monthly charts and table, the energy flow, the dispatch chart, the yearly table, the report and the workbook. With grid charging or a reserve they also show the grid's energy into the battery (comparison table, energy flow, dispatch chart, workbook), and with a reserve its hours held, energy cost and revenue.

**Critical load** (optional, Load page; off by default). *Critical share of the load* (100 % by default) splits the site load into a critical part, which must be served in every hour, and the rest. The plant's own auxiliaries count as critical. When supply falls short, through a grid outage, genset outages or an empty battery, the non-critical part is shed first: each step's unserved energy goes to the non-critical load up to its size and only the remainder to the critical load. The rule-based dispatch serves the same energy as without the split, so fuel and the other figures stay the same; what changes is the accounting and what the optimiser and the EMS make of it.
- Every year reports the critical load (`load_crit`), the unserved critical and non-critical energy (`unmet_crit`, `unmet_nc`, which add up to `unmet`) and the hours with more than 0.1 % of each part unserved (`lol_crit_h`, `lol_nc_h`); the result adds the unserved critical share of year 1 and of the worst year. The Simulation results, the report and the workbook show them.
- *Serve only the critical load while the grid is down* (Grid connection card, with a critical share below 100 %): during a grid outage the battery, the gensets, PV and wind serve the critical load alone, as with a backup panel behind a transfer switch, where the gensets feed critical circuits only (gap 18 of `docs/LITERATURE.md`). The non-critical load is shed for the whole outage: it counts as unserved non-critical load (`nc_shed` gives the part shed this way), and every outage hour is a loss-of-load hour. Without the option the plant tries to serve all the load during an outage and sheds the non-critical part only when it falls short.
- The optimiser's unmet-load and loss-of-load limits then hold for the critical load (below), and the predictive EMS prices unserved non-critical energy at its own value of lost load (below).
- At 100 % the results are the same to the byte as without the input.

**Deferrable load** (optional, Load page; off by default; gap 5 of `docs/LITERATURE.md`). A load that needs a set energy each day but not at set hours, such as a water pump or irrigation, on top of the site load. Inputs: the energy per day (or water per day and the energy per m³ pumped, which the app converts to energy; 0 turns it off), the maximum power, a window of the day in which it may run (from one hour to another, local standard time; it may run past midnight, and the same hour twice is the whole day) and a store that carries energy from one day to the next (a tank, in kWh or m³; 0 = none).
- Each step in its window the load takes PV and wind surplus, up to its power and to what it can still use: the rest of the day's energy and the room in the store. *PV and wind surplus goes first to* sets whether the battery charges before it (the default) or after it; either way it comes before export and curtailment. The battery first suits a load with a store, since stored battery energy can serve any load at night and the tank catches up on the next sunny day; the load first saves the battery's round-trip loss on energy it must draw that day anyway.
- It also draws, as late as its power allows, whatever the steps left in the window could not draw at full power: that part runs on whatever supplies the load in that step (PV, battery, gensets, grid), and the gensets are committed for it. With critical-only supply during a grid outage it runs on surplus only.
- When the window closes, the day's energy is taken from what the load drew that day and then from the store. Energy beyond the day's fills the store up to its size; the load never draws more than that, so the store cannot overflow. What neither covers is unserved deferrable energy. At the start of the simulation the store holds its initial fill, and a window already open counts as served for the hours before the start.
- When supply falls short the deferrable load is shed first, before the non-critical and the critical load: it draws the energy later in its window, or counts it short when the window closes.
- Accounting: the energy it draws is part of the load and of the energy served (so LCOE, COE and the renewable fraction include it), and its PV and wind are PV and wind to the load, so the load and PV balances close as before. Its shortfall is not in the unmet load, and the unmet-load fraction, the loss-of-load hours and the autonomy are taken against the site load. Every year reports its demand (`dl_demand`), the energy it drew (`dl_kwh`), the part from PV and wind (`dl_re`: its draw from surplus, and of the rest the share PV and wind had in the step's served load) and the unserved deferrable energy (`dl_unmet`); the hourly series have its power and the store's level. The Simulation results set the curtailment beside that of the same design without the deferrable load, run alongside, and the dispatch chart draws the load with and without it. The report and the workbook have the same figures.
- The diesel-only baseline and the PV-only reference serve the deferrable load too, so the savings compare the same demand. Load growth and the load multiplier of the sensitivity do not scale it.
- With the energy per day at 0 the results are the same to the byte as without the input.

Strategies:
- Load following: gensets serve only the load.
- Cycle charging: the battery covers the deficit as in load following until it is empty (or until gensets at minimum loading plus PV cover the load). The running gensets then charge it from their spare capacity to the SOC setpoint (capped at the maximum SOC), and until it gets there it discharges only to cover load the gensets cannot. No unit is started only to charge, and cycle charging does not look ahead to PV; while the battery holds, a rising load starts gensets that a discharge could have avoided. The hour in which a charge starts or ends is shared: a battery that runs empty part way through an hour is charged for the rest of it, and one that reaches the setpoint part way through discharges for the rest of it, so results do not move by whole hours when the battery size, its state of health or the setpoint change slightly. Units are still committed per hour, so genset starts change in steps. Earlier builds had no hold: the battery was topped up in one hour and emptied in the next, which gave far more cycles and starts and results that jumped between two patterns with small changes in battery capacity.
- Predictive EMS: see below.

### Time step, ramps and forced outages (`engine/src/sim/`)
- **Time step** (Diesel & control, *Time step*: 60, 30 or 15 min). The dispatch, the battery (power limits from the energy over the step, self-discharge per step), fuel and every count run in that step; energies are power × step length, hours are summed over the steps. Hourly data (PV, wind, auxiliaries, a synthetic or hourly load) are held over the hour or interpolated between the hour centres and scaled so each hour keeps its mean. A load imported from a 15 or 30 minute logger keeps that resolution (averaged in pairs for 30 minute steps). The predictive EMS plans hour by hour as before and follows each hour's plan evenly over its steps. Charts, tables, the report and the workbook show hourly means (fuel per hour, the state of charge at the end of the hour); *Export 15 min CSV* (or 30 min) on Simulation results gives every step. A 60 minute step gives the results of earlier versions to the byte.
- **Ramps and start time** (Gensets card). The online fleet's output changes by at most the ramp rate × its rating per minute over a step, up or down, and units cannot be shut down faster than that; a unit started in a step delivers only after the start time. What the gensets cannot follow falls to the battery, then to unmet load; output they cannot shed goes to the battery or is dumped. Steps held back count as ramp-limited hours.
- **PV and wind ramp limit** (Diesel & control, *PV and wind ramp limit*, 15 and 30 minute steps only; 0 = off). A grid code may cap how fast a plant's output changes at the point of connection, in % of its rating per minute; [51] sizes a battery for such smoothing. The rating is the PV inverters' AC rating (kWp ÷ DC/AC ratio) plus the turbines' rated power, and PV and wind may change by the limit × the step's minutes in one step (at 15 minutes, 1 %/min allows 15 % of the rating; above 6.7 %/min the limit never binds). The limit acts twice in each step, around the usual order.
- **Ramp limit, a rise** (first). PV and wind above the last step's output plus the limit charge the battery (within its power, its SOC window and a frequency reserve's band), and what the battery cannot take is curtailed. The allocation then works with the limited output, so the gensets, the battery and the grid are dispatched against what the plant actually delivers. A rise has to be cut before the allocation, since the unit commitment and the battery's charging depend on it. When the battery also discharges for the load in that step, only the difference flows: the rise reaches the load through the battery.
- **Ramp limit, a fall** (last). The usual allocation already sends the battery in before the gensets wherever its strategy lets it, so a fall needs nothing more where the battery covers it. What the battery gives more than in the last step counts toward the fall; for the rest of the fall beyond the limit it discharges further (within the same limits, also when cycle charging or the EMS plan held it back) in place of unserved load, genset output above minimum and grid import. What it cannot give is a *ramp violation*: the fall landed on the gensets, the grid or the load. A fall that the bus would not have seen (PV and wind still covering everything they served) is no violation.
- **Ramp limit, results**. Results give, per year, the violations (steps and energy), the battery energy charged and discharged for the limit, and PV and wind curtailed by it (also in the curtailment). Simulation results compare curtailment and battery throughput with the same design without the limit, run beside it. The battery's own dispatch is not ramp limited: with load following the battery may pass the energy it took on a rise to the load in the next steps. **The PV and wind data are hourly**, held or interpolated into the steps (*Interpolated* is the better choice here), so a step shows only the slope between hour means, never a cloud passing. The figures are therefore a lower bound on the battery work and curtailment a ramp limit needs; sizing a battery for it properly takes minute data, which Soloptima does not take. No synthetic variability is added: the engine has no sub-hourly irradiance model to scale noise by, and noise without one would only look precise. At a 60 minute step the input is ignored, and the simulation says so.
- **Forced outages** (Gensets card). Each unit fails at random (exponential time between failures at the set rate per unit and year) and is out for an exponential repair time; out units cannot be committed and the units always online are capped at those available. Each project year and unit has its own draw from the seed. Results give the outages and the unit-hours out.
- **Random inverter and PCS outages** (PV card, Battery card). A flat availability spreads downtime evenly over every hour,
  which hides the risk that matters in a hybrid: an inverter block or the battery's converter being out for days, maybe
  in the one week the plant is short. These draw it instead, the same way as the genset outages.
  - *PV:* the plant is split into inverter blocks of the size you give (PV capacity / DC/AC ratio / block size, rounded
    up, so it follows every size the optimiser tries). Each block fails at random at its rate per year (exponential time
    between failures, in calendar time) and stays out for an exponential repair time. While it's out, its share of the PV
    output is gone. The results give the outages, the block-hours out and the PV energy lost.
  - *Battery:* the battery's power is split over PCS units the same way. A unit out takes its share of the charge and
    discharge power, and of the spinning reserve the battery counts for. The stored energy stays, shared by the units still
    running. With one unit, a failure stops the battery until it's repaired.
  - *The EMS:* the predictive EMS knows which blocks and units are down when it plans (an operator would), and plans with
    what's left. It doesn't know about failures to come.
  - *Seed:* the genset seed (Diesel & control) draws all three, each kind apart, so turning inverter outages on doesn't
    move the genset outages. The same seed gives the same outages every run; change it to see another year.
  - *Don't count it twice:* the flat *Availability* on the PV card still applies on top. A unit with failure rate r a
    year and mean repair R hours is out R / (8760 / r + R) of the time, so lower the flat availability's downtime by that
    much, or set it for what's left (grid, scheduled maintenance). For example 0.5 a year with 72 h repairs is 0.4 %.
  - The rates default to 0. A project that doesn't turn them on gets exactly the results it had before.
- **Minimum up and down times** (Gensets card, 0 by default). A unit started stays online at least the minimum up time; its output at minimum loading that the load does not take charges the battery or is dumped. Only a forced outage takes it off earlier. A unit stopped stays off at least the minimum down time. This wins over the spinning reserve, battery charging and the units always online, but not over the load: when the load would go unserved with the battery at its full discharge and the grid at its import limit, just the units the load needs start, and each year counts these early restarts. The reason for the order: a short reserve or a missed charge costs little and shows in the reserve shortfall, while unserved load is the failure the plant is there to prevent. The units count as alike: a stop takes the unit that has run longest, a start the one that has been off longest. In a mixed fleet the times apply to the number of units online, and the merit order still picks the groups. All three strategies and the diesel-only baseline keep the times; the predictive plan does not see them, and real time holds them.
- **N-1 check** (Gensets card). Every step with gensets online, the output of the largest online unit, lost at once, is set against the headroom of the other online units, the battery reserve and the grid's spare import; steps where it is not covered count as N-1 shortfall, with the largest gap. It reports the exposure; it does not commit extra units.

### Operational adequacy (`engine/src/sim/`)
Unmet energy alone says little about how often supply fails, so every year also records:
- loss-of-load hours (more than 0.1 % of the hour's load unserved), events (runs of such hours) and the longest event; with a critical share, the unserved energy and loss-of-load hours of the critical and the non-critical load apart (Dispatch above);
- reserve shortfall: hours in which the genset headroom (genset charging counts as headroom) and the battery reserve left after dispatch do not cover the spinning-reserve rule, and the largest shortfall in kW. The PV and wind part counts only the power the load would lose if PV and wind fell by the reserve share, since curtailed and charging power absorbs the drop first;
- most gensets online, hours with the whole fleet online, hours with every online genset at minimum loading and the longest such run (wet stacking), and most gensets started in one hour.

Reliability in time (`summary.rs`, `result.summary.reliability`): the longest run of low-PV days in the weather year actually simulated, where a low-PV day yields less than a share of the mean daily PV yield (*Low-PV day* in the Dispatch strategy card, 50 % by default; AC output per kWp, local days, December does not run on into January), with its first day and the number of low days in the year; and the longest run of hours in year 1 with more than 0.1 % of the load unserved, with its first hour. They are reported, not used as constraints. The days of autonomy constraint of the optimiser is below.

With enough units for the peak load and its reserve, the shortfall is normally zero for both the hybrid and diesel only. It shows a fleet that is too small: one unit fewer for maintenance, a few large units, load growth. The Simulation results page compares these with diesel only, draws the units online duration curve, and lists notable weeks to open in the dispatch chart (highest unmet load, most gensets online, lowest renewable share, highest curtailment, lowest SOC, longest low-load run, best PV week). The report adds the dispatch of the lowest-renewable week. Firm capacity is set by the peak load and the reserve rule, so the duration curve shows daytime unit-hours freed for maintenance, not units that can be retired.

### Outage survival (`engine/src/sim/resilience.rs`)
*Outage survival* on the Simulation results page shows how long the plant carries its critical load when the grid fails, the figure tenders often ask for, after [44]. It runs as a job of its own with progress and Cancel, so a normal simulation stays as fast as before.
- Starts and lengths: an outage begins at every hour of year 1 (or every *n* hours, 1 to 168) and runs up to the longest outage set (336 h, two weeks, by default; at most 720 h). The year wraps round, so an outage that starts late in December runs on into January.
- Each outage starts from the stored energy the normal simulation had at the start of that hour, with that hour's PV and wind (year 1, inverter outages included) and the critical load (Dispatch above; all the load without a critical share). A deferrable load is left out: it waits for the outage to end. Nothing is imported or exported. Off grid the study reads as the plant riding through genset failures.
- Dispatch in the outage, every hour, a simple balance without a planner: PV and wind serve the critical load; the gensets that work cover what is left and recharge the battery from their spare capacity, with just the units needed for that and at least their minimum loading; the battery covers the rest. There is no spinning reserve, ramp limit or minimum up time, and fuel is unlimited (the model has no fuel tank). An hour is served in full when no more than 0.1 % of its critical load is unserved, as for the loss-of-load hours.
- Gensets: a unit is available at the start with probability OA = 1 / (1 + rate × repair time / 8760) from the forced-outage inputs, starts with probability 1 − FTS (*Failure to start*, Gensets card, 0 by default) and then runs for an exponential time of mean MTTF (*Mean running hours to failure*; 0 takes 8760 ÷ the forced-outage rate, and with both at 0 units do not fail). So a unit still runs after d hours with probability R(d) = OA (1 − FTS) e^(−d/MTTF), the unit model of [44]. A failed unit is not repaired within the outage.
- In a mixed fleet every group takes the availability, failure to start and time to failure of the main genset inputs; the groups have no reliability inputs of their own.
- Probability: the study simulates each outage once for every combination of working units (by genset group in a mixed fleet; at most 1024 combinations), with those units working throughout. The units still working at hour d are binomial with R(d), group by group, so each combination's chance is a product of binomial terms, and the survival is the sum over the combinations that have served every hour so far. There are no random draws, so the answer is the same every run. With this dispatch more working units never serve less, which lets the study count a unit that fails part way through an outage as if it had been out from the start: exact without a battery, and slightly low, on the safe side, where the battery bridges a gap after a failure. [44] follows the units and the stored energy together in a Markov chain over SOC bins instead, which takes far longer. A combination that served the whole outage is not simulated again with more units.
- Results for each outage length d: the cumulative survival, the chance that the critical load has been served in full in every hour of the first d hours, as its minimum, 5th percentile and mean over the start hours and the share of start hours below 90 %; the chance that hour d itself is served whatever happened before, the hourly figure [44] plots, as a mean and a minimum; and the expected share of the critical energy served over d hours. The cumulative figure is the one to quote: a site that loses its critical load once has failed, while the hourly figure counts hours served again after the sun comes back and stays higher. The chart draws both, with R(d) of one unit when gensets can fail; the table gives the usual lengths and the heat strip the cumulative survival of one length by day and hour of start.
- The report has the chart, the table and the strip, and the workbook an *Outage survival* sheet (every length) and a *Survival by start* sheet. The result is kept for the session and is not saved with the project.
- Time: on the example study (20 × 1800 kW gensets, 8760 starts, outages up to 336 h, 2.9 million plant-hours per combination of units) a study takes 0.1 to 0.2 s with failure to start and running failures set, about 0.3 s with the predictive EMS (its year-1 run included) and 0.6 to 0.8 s with the fleet split into 100 units of 360 kW, on a 10-core laptop in a release build.

### Auxiliary loads (`engine/src/sim/`)
The plant's own consumption is added to the load and dispatched with it every hour, also at night when it costs diesel:
- battery HVAC, BMS and fire system, in kW per MWh of nameplate energy, rising by a coefficient per °C of hourly ambient temperature above a reference (with a battery);
- the no-load loss of the battery inverters (PCS) while energised, in kW per MW of PCS rating (with a battery); it follows each candidate's battery power in the optimiser, so a higher C-rate pays for its larger PCS;
- plant auxiliaries (SCADA, lighting, tracker motors), with PV, wind or a battery;
- the no-load loss of the PV step-up transformers (with PV) and of the BESS step-up transformers (with a battery), so the PV-only reference and designs without a battery do not pay for the battery's transformers.

They do not grow with the load, and the diesel-only baseline has none. LCOE, COE and the renewable energy billed in Project finance count only the energy served to the site; unmet energy is attributed to the site load first. The predictive EMS and the day-ahead schedule plan with the auxiliary load as known (the schedule at the forecast temperature). Enter the battery standby draw here rather than in the round-trip efficiency, which charges it only when energy passes through the battery. The PCS no-load loss counts in every hour, so in hours with battery flow it overlaps slightly with the round-trip efficiency; for a PCS that sleeps while the gensets carry the load, enter its standby draw.

### Battery ageing (`engine/src/sim/`)
State of health (SOH) falls every year by:
- calendar fade, a fixed loss per year;
- cycle fade = DC equivalent full cycles × (1 − end-of-life SOH) / (cycle life × rated depth of discharge). DC cycles are the energy taken from the cells (AC discharge ÷ one-way efficiency) divided by nameplate energy. A battery rated 8,000 cycles at 95 % DoD therefore reaches end of life after 7,600 full-nameplate cycles.

The battery is replaced when its SOH falls to the replacement threshold (blank = the end-of-life SOH), except in the last project year, and the new one starts at 100 %. The end-of-life SOH only sets the fade per cycle, so the threshold can differ from it. Fade is linear; real cells fade faster below their datasheet end of life (capacity knee), so a lower threshold is optimistic. An existing or second-life battery starts at its initial SOH (set its capex to zero). The salvage value at the end of the project is the cost of the battery in service times its SOH left above the threshold, as a share of the SOH it had above the threshold when installed.

The *Battery health* card on the Simulation results page shows the SOH curve with the threshold and the replacement years, and the calendar and cycle fade of each year. It also shows the highest cycles per year (AC discharge ÷ nameplate energy, with the DC value alongside) against the warranty cap, the highest C-rate used, the expected life of a new battery at year-1 use, with the term that limits it, and its autonomy: the hours the usable energy of the battery at its starting state of health (SOC window × one-way efficiency) carries the year-1 mean load alone.

**Cycle life by depth of discharge** (optional, Battery page, *Ageing*; also a field of the battery datasheets). Cells last more cycles when they are cycled shallowly, and the linear model above gives shallow cycling no credit. Enter two to four points of the datasheet's cycle-life chart as `DoD %: cycles`, e.g. `10: 60000, 50: 9000, 100: 4000`; they replace the cycle life and its depth of discharge. Then (`engine/src/sim/ageing.rs`):
- The stored energy of every time step, as a share of nameplate energy, is counted by rainflow (ASTM E1049-85, three-point method [41]) over each year: the series is reduced to its peaks and valleys on a stack, closed cycles count as one, and what is left at the end of the year counts as half cycles. The count is O(n) per year.
- Each cycle of depth D uses 1 ÷ N(D) of the cycle life, where N is the curve, and the year's cycle fade is (1 − end-of-life SOH) × Σ count ÷ N(D) (Miner's rule [42]). Between points N is a straight line on log-log axes. Shallower than the first point or deeper than the last, the energy to end of life of that point (cycles × depth) holds, so the curve gives no extra life outside the range the datasheet covers.
- Depth is measured against nameplate energy, as the linear model counts its cycles, so a curve with the same cycles × depth at every depth gives the fade of the linear model (`cargo test` checks this to 2 %).
- Calendar fade, the replacement threshold and the salvage value work as before. The *Battery health* card and the report add the rainflow cycles of year 1, their mean depth and the share of the cycle life they use; the workbook's *Yearly* sheet has them for every year (`rf_cycles`, `rf_dod`, `bess_damage`).
- The predictive EMS prices wear at the replacement cost over the energy to end of life of a cycle across the whole SOC window: replacement cost ÷ (N(window) × window) per kWh discharged. That is the deepest cycle the battery makes in normal use, so the price is on the high side for a plan that cycles shallowly; the real-time fade is still counted cycle by cycle.

Earlier versions counted cycles on the AC side. Counting them at the cells raises the cycle fade by 1/√RTE (6.6 % at 88 % RTE), so replacements can come earlier than before.

### Forecast-based EMS (`engine/src/forecast/`, `engine/src/ems/`)
The EMS is model-predictive control with dynamic programming:

1. Forecast (at every re-plan, by default every hour, using only data observed so far). PV and load forecasts are made for the next *H* hours (default 24). Wind is forecast too when turbines are present.
2. Plan with a backward dynamic programme over the battery's stored energy, discretised into n levels (SOC resolution setting, default 21, at most 101). n is raised when one level step would exceed half the energy the battery can charge in an hour at rated power.
   - The cost of each hour *h* and level change is fuel(units, loading) × price + genset O&M (per run-hour and per kWh) + battery wear (replacement cost / (cycle life × its rated DoD) per kWh discharged, or with a cycle life by depth of discharge, replacement cost / (N(SOC window) × SOC window); see Battery ageing) + value of lost load × unserved energy. With a critical share below 100 % the forecast load of each hour has a non-critical part, and unserved energy up to it costs the *value of lost non-critical load* (blank: the value of lost load) instead; set it lower and the plan keeps stored energy for the critical load. With critical-only supply the plan takes the non-critical load out of the hours it knows the grid is down (the daily pattern, and the hour in progress). The day-ahead schedule does the same.
   - *Plan with the cost per genset start* (EMS setting, off by default): each unit the plan starts costs the price per start of the Costs page. The state of the programme is then the stored energy and the units online in the hour before, so a path that stops a unit for an hour and starts it again pays for the start. The units after an hour lie in the narrow range that hour's level changes give, so this costs about three times the planning time of the plan without starts (5.7 s against 1.8 s for a predictive run of the example study). On the example study with a price of 60 per start it cut year-1 starts from 4,798 to 4,200 for 0.04 % more fuel; with the forecast errors of that run the NPC came out 0.006 % higher, with perfect forecasts it came out lower. Whether it pays depends on the price per start against the fuel a unit burns at minimum loading. Minimum up and down times are not part of the plan; the real-time dispatch holds them.
   - Units committed = ⌈(net load − battery + spinning reserve − battery reserve) / unit rating⌉, at least the minimum online, with genset minimum loading enforced.
   - *Keep reserve energy in the battery* (EMS setting, off by default): the hour cost of a level change from k to m then credits as battery reserve only what the energy above the minimum SOC sustains for the reserve duration (at the lower of the two levels, less the hour's discharge), the rule real time applies. Low levels then cost the genset units the reserve needs, so the plan can hold energy back as reserve instead of starting a unit. The hour costs are tabulated by level change as below and recomputed only where the energy limit binds, which makes planning about four times slower; on the example study with the predictive EMS it saved about 5 % of genset run-hours and 0.1 % of fuel in year 1.
   - Otherwise the DP credits the battery's spare power as reserve whatever its stored energy. Once the path is chosen, its units are recomputed with the battery reserve limited as in real time: the energy above the minimum SOC at the start of the hour ÷ the reserve duration, less the hour's discharge. The plan therefore no longer leaves out units that real time must start, at any reserve duration. Predictive results moved slightly with this change: year-1 fuel up to 0.004 % higher on the example study.
   - The hour cost depends only on the level *change*, so it is tabulated once per hour. A plan costs at most H × (2n − 1) cost evaluations plus H × n² additions (24 × 41 and 24 × 441 with the defaults), and fewer when the battery power limits the level change in one hour.
   - Energy left at the end of the horizon is valued at the fuel it would displace (terminal value), so the plan does not empty the battery just because the horizon ends.
   - A deferrable load (Dispatch above) is scheduled before the battery is planned: the energy each window in the horizon still needs (the store drawn first) goes to the hours of that window where its power costs least in the plan's own hour cost with the battery idle, so hours of forecast PV and wind surplus come first, then cheap import or genset hours. That load is added to the forecast load, and the programme plans the battery around it. Real time runs the planned power, takes any surplus the forecast missed, and keeps the rule that finishes the window in time. A window that ends beyond the horizon is left to a later plan. This is a heuristic, not a second state of the programme: a state for the store would multiply the planning time by its number of levels (the battery alone has 441 level pairs per hour with the defaults), while the schedule costs two hour-cost evaluations per window hour, so the predictive run of the example study takes 1.72 s with a pump of 60 MWh a day against 1.68 s without. It does not trade the load against battery charging in the same hour; the plan sees the load as fixed once scheduled.
   - With a grid connection the hour cost includes the import at the hour's price and the export revenue. With *Charge the battery from the grid* the grid covers planned charging in hours it is cheaper than the gensets, and the terminal value is capped at the cheapest import of the horizon. With a *frequency reserve*, in hours the grid is planned up, level changes that need more than the battery power less the reserve are left out and levels outside the reserve's band cost 10 × the value of lost load per kWh. The day-ahead schedule plans the same way.
3. Act until the next re-plan (by default the first hour only): steer toward the planned state of charge, then re-plan (receding horizon).
4. Compensate in real time. The battery absorbs a forecast error only when the error would otherwise force an *unplanned genset start*. It first drops planned genset charging, then discharges just enough (found by bisection). Diesel marginal fuel is almost flat, so moving energy through the battery to fix every small error would only add round-trip losses. Surplus PV/wind always charges the battery. Optional *firm commitment* keeps the units committed in the current plan online even when the actual net load is lower.

**Forecasting methods** (all causal; PV methods work on the clear-sky index, load methods on load relative to its mean):

| Method | PV | Load | Idea |
|---|---|---|---|
| Persistence | ✓ | ✓ | same hour yesterday (baseline for the skill score) |
| Seasonal naive (weekly) | | ✓ | same hour last week (weekday/weekend) |
| Smart persistence | ✓ | | clear-sky output × clear-sky index of the last 3 h blended into the last 24 h |
| 7-day profile + persistence | | ✓ | mean of the same hour over 7 days + decaying latest deviation |
| 30-day climatology | ✓ | ✓ | mean index of that hour over the last 30 days |
| Exponential smoothing | ✓ | ✓ | exponentially smoothed level per hour of day + decaying correction from the latest hour |
| Adaptive regression (RLS) | ✓ | ✓ | lead-specific linear model (11 lead buckets, 5 features + intercept) learnt online by recursive least squares |
| Analog ensemble (k-NN) | ✓ | ✓ | the 7 of the last 60 days whose last-24-h pattern best matches now; average of what followed |
| Adaptive ensemble | ✓ | ✓ | blend of five members (PV: smart persistence, climatology, smoothing, RLS, analog; load: profile, weekly, smoothing, RLS, analog), weights ∝ 1 / MSE over the last 14 days, separately intraday (lead < 6 h) and day-ahead |
| Neural network (MLP) | ✓ | ✓ | 10-16-16-1 ReLU network trained with Adam on lagged indices, lead time and calendar; retrained monthly on the preceding 330 days only (causal) |
| Perfect / perfect + noise | ✓ | ✓ | benchmarks: the forecasting ceiling, and robustness to a chosen error level |

The **Forecast Lab** benchmarks all of them over horizons of 1–48 h (nMAE, nRMSE, bias, skill vs persistence). It also re-runs the EMS with each method to show the fuel, genset-hour and NPC value of better forecasts.

The Lab also splits the errors by weather class. Each day of the year is clear, cloudy or overcast by its daily clear-sky index, the PV energy of the day over the clear-sky PV energy of the same system (the reference the PV methods use): clear above 0.7, cloudy from 0.3 to 0.7, overcast below 0.3. These thresholds are a convention of this tool, not taken from a source. For each class and method it gives nMAE and nRMSE, both divided by the mean of the whole year so that the classes add up to the year's figures, and the skill against persistence on the same days. Load methods are split by the same days. The table on the Forecast & EMS page and in the report shows 24 h ahead; the workbook also has 1 h ahead and the hours of each class.

**Operational day-ahead schedule.** This pulls a live weather forecast: Open-Meteo [27] irradiance, or MET Norway [28] cloud cover converted to irradiance via Kasten-Czeplak [29]. It runs the same PV model and planner from the current SOC and outputs hourly genset commitment, battery set-points and fuel, exportable as CSV.
- The plan starts at the current hour of the computer's clock, and the SOC you enter applies at its start. Open-Meteo's forecast begins at 00:00 UTC, so its hours already past are dropped (one more day is fetched to make up for them); MET Norway's begins at the current hour. *Days ahead* × 24 hours are planned.
- Each row is the mean over its hour: Open-Meteo's irradiance is the mean of the hour before its timestamp, and MET Norway's cloud cover, temperature and wind are averaged from the forecast instants at the start and end of the hour. The load is averaged over the same hour. The table and chart label each row by the start of its hour in local time; in the CSV, `time_utc` and `time_local` are the provider's stamp and `start_local` the start of the hour.
- The hours are planned one after the other, also across 29 February. The forecast ends at the first hour without irradiance or temperature (Open-Meteo returns empty values past the end of its model's range), so missing data is never read as zero PV.
- With wind turbines, their output on the forecast 10 m wind (the project's shear, power curve, losses and availability) is added to PV, as in the lifecycle simulation, and the plan commits gensets for the net load.
- The status line gives the provider, when the forecast was fetched and, for MET Norway, how old its model run was at that time, with a warning above 12 h. The CSV starts with a comment line holding these, the plan start and the SOC entered.
- *Both, blended with fixed weights* fetches Open-Meteo and MET Norway with the same two requests as the single providers and takes, hour by hour, the weighted mean of their irradiance, temperature and wind. *MET Norway share of the blend* sets the weights (50 % each by default). Rows are matched by the hour they cover, so the blend covers the hours both forecast and stops where MET Norway's hourly data ends. Open-Meteo's split into beam and diffuse light is kept as a share of the blended irradiance. The weights are fixed by the user: the live schedule has no measurements from the site, so it cannot learn them the way the adaptive ensemble and the regression of the Forecast Lab learn theirs from the past year. The status line names both providers and the weights.
- Forecasts and the plan are hourly. With a 15 or 30 minute time step the predictive EMS of the simulation still plans hour by hour on hourly forecasts and follows each hour's planned battery energy evenly over its steps, while the actual PV within the hour is held or interpolated between the hour centres as *Hourly data in shorter steps* sets it (each hour keeps its mean). The forecasts are not interpolated: the plan works in whole hours, so finer forecast values would not change it. The day-ahead schedule is hourly.
- Open-Meteo's free API is for **noncommercial** use only; commercial use of its forecasts needs an Open-Meteo API key. MET Norway data is CC BY 4.0.

### Economics
Nominal discounted cash flow over the project life: capex (PV, BESS energy + PCS, wind, optional new gensets, development margin), fuel with escalation, O&M with escalation (PV per kWp, BESS per kWh, wind per kW, gensets per kWh and per unit run-hour), genset starts at a price per start (0 by default; with a price, each year reports the cost of its starts, `c_starts`, which is part of the genset O&M, and the results, the report and the workbook show it beside the start count), genset overhauls and replacements by run hours (below), replacement of the PV inverters and of the battery PCS (each with its own year and cost per kW; the PCS takes the inverter values when left blank), wind-turbine replacement, battery replacements at the replacement threshold with price decline, carbon price and pollutant prices (below), linear salvage. LCOE = NPC / discounted energy served to the site (auxiliary consumption excluded). IRR / payback on the incremental cash flow vs the diesel-only baseline (same fleet, same reserve rules; with a grid connection, grid + diesel). Grid energy, demand charges and export revenue are a yearly cost of their own, and the revenue of a priced frequency reserve comes off the yearly cost (project finance does not take it as revenue). The battery's own value uses the same incremental cash flow against PV only (below).

**Genset wear** (`sim/econ.rs`, off by default). Run hours are counted, and with an overhaul interval or a life in run hours (Costs page, and per group in the mixed-fleet editor) the gensets are overhauled and replaced when they reach them [43].
- The dispatch commits a number of units of each group, not named ones, so the units of a group are taken to share its unit-hours evenly, as they do when the operator rotates the lead unit. Each unit's run hours add up over the project years, and both units of a two-unit group reach an interval in the same year.
- A unit is overhauled each time its hours pass a multiple of the overhaul interval within its life; an overhaul that falls when the unit is due for replacement is the replacement. After a replacement the count starts again.
- Overhauls and replacements are booked in the year they fall due, at today's prices per kW of the unit's rating (per kW like the genset capex, so one figure fits every unit size and every fleet size the optimiser tries), and enter the replacements and the NPC, discounted like the other replacements. None is booked in the last project year, as for the other components.
- At the end of the project the life a unit has left (life minus its hours since it was installed or replaced) is credited as linear salvage at the replacement cost. Without a life, overhauls alone run on and nothing is credited.
- The replacement cost defaults to the genset capex per kW. Gensets already on site (capex 0) still wear out, but a blank replacement cost then makes their replacement free, so enter the price of a new unit for them. Their salvage is valued at the same replacement cost, so the hybrid and the baseline are both credited for the life they leave. Units start the project at 0 h.
- The diesel-only baseline wears out the same way, so a hybrid that runs its gensets less shows the overhauls and replacements it saves in the NPV, IRR and payback. Project finance takes the wear as a running cost of the host (with fuel and genset O&M), not as a replacement of the new assets.
- Each year reports `gen_overhauls`, `gen_replacements`, their costs `c_gen_overhaul` and `c_gen_replace` (in `c_replace`) and, in the last year, `c_gen_salvage` (in `c_salvage`); a mixed fleet's groups add `overhauls` and `replacements`. The results show the totals beside the run hours and in the yearly table, the report beside the run hours, and the workbook in the *Yearly* and *Genset groups* sheets. If the O&M per run-hour already includes major overhauls, take them out of it.

**Emissions and pollutant prices.** CO₂, NOx, SOx, PM2.5 and CO are fixed masses per litre of fuel (PM2.5 and CO 0 by default), so the fuel curve, which burns more litres per kWh at part load, already raises them per kWh at low loading. CO₂ adds the grid's factor on imports and, when set, an embodied factor per kWh of PV output (curtailed output included, since the emissions of making the modules do not depend on how much is used; `co2_pv_t`). The carbon price is per tonne of CO₂; NOx, SOx, PM2.5 and CO each have a price per kg (0 by default); [43] prices NOx and PM2.5 the same way. Their sum is a yearly cost of its own, `c_pollutants`, in the yearly cost and the NPC like the carbon cost, for the hybrid and the diesel-only baseline alike; project finance takes it with the carbon cost. With a grid connection the pollutant prices also enter the cost of genset energy that the grid price is weighed against. With PM2.5, CO or a price set, the results show PM2.5 and CO beside NOx and SOx, the comparison table and the report the pollutant cost, and the workbook the yearly masses and cost.

Grid-extension break-even (`sim/econ.rs`, off by default): for an off-grid design, a line cost per km on the Grid connection card (shown while the connection is off) gives the distance at which extending the utility line costs as much as the designed plant. The net present cost of grid supply over L km is the connection cost + L × cost per km + the discounted line O&M (per km and year, escalated with the O&M escalation) + the site load of each simulated year at the grid energy price, escalated by its own rate, over the project life at the project discount rate. The whole site load counts as grid supply, the load the plant leaves unserved included; the plant's auxiliary consumption does not. No salvage, losses, demand charge or grid outages are counted. The break-even distance is where this equals the plant's NPC; 0 means the grid costs more even with no line. The Simulation results show it as a tile, the report under Economics and the workbook in the Summary sheet.

### Diesel-only baseline against site records (`ui/src/screens/sim/`)
Every result is measured against the modelled diesel-only case: fuel saved, NPV, IRR and the battery's own value. For an existing plant, *Existing diesel plant records* on the Diesel & control page takes what the site has recorded: site load, peak load, genset generation, fuel, run hours of all units and the fuel of each month, with the period, source and scope of the records. Blank fields and fields entered as zero are left out. The Simulation results page compares them with the diesel-only case of the last run (year 1, without auxiliary loads), as model ÷ site − 1:
- flagged beyond ±3 % for the site load and the generation, ±5 % for the peak, the fuel and the specific fuel consumption (L/kWh), and ±10 % for the run hours;
- the monthly fuel is drawn against the records, with its CV(RMSE) and the months more than 15 % off. Fuel records are often deliveries, so a change in tank stock moves fuel between months.

Fixed rules suggest where a gap comes from; nothing is applied to the model. A load that matches with a fuel that does not points to the fuel curve or the units online. More recorded run hours than the model mean the operators run more units than the reserve rule, and the hybrid's savings assume the modelled practice. A generation that matches with a specific consumption that does not points to the fuel curve, with the factor that would match. A load, peak or generation that differs points to the load profile (station service, losses, metering point). The card also gives the leverage: each 1 % of error in the baseline fuel alone moves the fuel saved by baseline fuel ÷ fuel saved %, 5.2 % on the example study. An error in the fuel curve moves the baseline and the hybrid together, and the fuel saved by about 1 % per 1 %. The report shows the check under Energy simulation, and the workbook has a *Baseline check* sheet.

### Results check (`engine/src/sim/checks.rs`)
After every simulation the engine compares a few results with a plausible range and lists those outside it, each with its value, the range and a one-line reason, on the Simulation results page (a card shown only when something is listed), in the report under Energy simulation and in the workbook's *Summary* sheet. The ranges are wide on purpose, so a sound project raises nothing; a check that fires points at an input slip (a unit, a factor typed twice, irradiance in the wrong unit) or at a figure that does not add up. Nothing is changed. The checks:

| Check | Range | Why |
|---|---|---|
| PV performance ratio, year 1: PV output available per kWp ÷ plane-of-array irradiation (after shading) | 50 % to 95 %; with bifacial modules the top rises by the rear irradiation's share of the front | Losses from temperature, soiling, wiring, the inverter and clipping take between about 5 % and half of the output; outside that the irradiation, the size or the losses are wrong |
| PV capacity factor, year 1, on the DC rating | at most 35 % | Single-axis trackers at the sunniest sites stay below about 30 % |
| Wind capacity factor, year 1 | at most 65 % | The best onshore and offshore sites reach about 50 to 60 %; more points to the wind speeds or the hub height |
| Genset specific fuel consumption, year 1 (fuel ÷ genset energy) | 0.2 to 0.6 L/kWh | Gensets run between about 0.21 L/kWh near full load and 0.5 at low loading; the reason gives the efficiency at 9.94 kWh/L (diesel's lower heating value, about 35.8 MJ/L) |
| CO₂, NOx, SOx, PM2.5 and CO per litre of fuel, year 1 (grid and embodied PV CO₂ taken off) | the factor entered ± 0.1 % | The year's mass divided by its fuel must give the factor back |
| Energy balance, every year: PV, wind and genset energy, grid import and unserved load against the load, curtailment, genset dump, export, battery losses, self-discharge and the change in stored energy | ± 10⁻⁶ of the inputs (at least 1 kWh) | Every kWh has to go somewhere; the worst year is shown |
| LCOE recomputed: capex plus the yearly costs discounted, over the energy served to the site discounted | the LCOE reported ± 10⁻⁶ | The same as the annualised cost (TAC) over the annualised energy; the LCOE must follow from the yearly figures |
| LCOE against the diesel-only case | 0.1 to 10 times | A factor of ten either way usually means a cost entered per W instead of per kW, or per MWh instead of per kWh |
| Payback against diesel only | between the year before and the year in which the cumulative incremental cash flow (capex difference, then the yearly cost difference) first turns positive; never when it does not | Payback must agree with the cash flow it comes from |
| Battery equivalent full cycles, highest year (AC discharge ÷ nameplate) | at most 8,760 × the C-rate (power ÷ energy) | The battery cannot discharge more than its power for every hour of the year; the warranty cap is checked on the Battery health card |
| Battery round trip implied by year 1, from the energy charged and discharged with the change in stored energy and self-discharge | the round trip entered ± 1 percentage point (with at least one full cycle) | The dispatch charges and discharges at the efficiency entered, so the year must give it back |

The emission, balance, LCOE, payback and round-trip checks hold by construction in the engine; they guard the report's figures against a change that breaks them, the kind of slip gap 22 of `docs/LITERATURE.md` found in published studies. The checks run in `simulate` beside the summary, so no output that the parity tests hash changes.

### Gensets by month, state of charge by season, renewable fraction (`ui/src/lib/sim-tables.js`)
The interface computes these from the year-1 hourly series of the simulation:
- **Gensets by month** (Simulation results, report, *Genset monthly* sheet): run hours of all units, starts (units added from one step to the next, the first hour of the year included, as the engine counts them; from the steps of a run under an hour), energy, fuel, capacity factor = energy ÷ (fleet rating × hours of the month), specific fuel (L/kWh) and efficiency = energy ÷ (fuel × 9.94 kWh/L). The year row adds up to the year-1 totals.
- **Battery hours by state of charge and season** (Simulation results, report, *SOC by season* sheet): the hours of year 1 in each 10 % band of state of charge at the end of the hour, against the battery's capacity that year (nameplate × state of health), for each season (Dec–Feb, Mar–May, Jun–Aug, Sep–Nov) and the year. The bands add up to the hours of each season.
- **Renewable fraction** three ways (tiles of the indicators card, report, *Summary* sheet). *By energy*, the headline: 1 − energy from the gensets and the grid ÷ energy served (year 1). *By capacity*: PV kWp and wind rating ÷ those plus the rating of the genset fleet the run used (the grid connection and the battery are not generating capacity). *By peak*: the highest share of an hour's load that PV and wind serve directly in year 1 (the instantaneous penetration the gensets and the controls must cope with).

### Battery value and operating options (`engine/src/api/`, `ui/src/screens/sim/`)
Every simulation also runs the same PV and wind without the battery (PV only); without a battery every strategy reduces to load following. The battery's own NPV and IRR come from the incremental cash flow of the hybrid against PV only, so its capex, O&M, replacements and salvage are weighed against the fuel and genset costs it avoids. A hybrid can beat diesel only by a wide margin while its battery loses money. The *Battery adds* tile shows this NPV (in red when negative), and the comparison table gains a PV-only column. PV only keeps the hybrid's PV capacity, so it usually curtails more than a design without a battery sized on its own. After an optimisation the *Best PV-only design* tile gives the cheapest ranked design without a battery.

*Compare options* on the Simulation results page runs one batch of the project with one setting changed per row: diesel only, PV only, the battery with load following, with cycle charging to 60, 80 and 100 % SOC (capped at the maximum SOC; rows that coincide after the cap run once), with the predictive EMS and the project's forecasters, and with the predictive EMS and perfect forecasts (a benchmark for better forecasting, not an option; the EMS plans over a rolling horizon, so it does not always give a lower NPC). The table gives fuel, renewable fraction, genset hours and starts, battery cycles and replacements, curtailment, unmet load, capex, NPC, LCOE, NPV and IRR against diesel only, equity IRR, and the NPC change from the row above. It highlights the lowest NPC that meets the optimiser constraints and marks differences below 0.5 % of NPC as within model accuracy. A waterfall splits the NPC from diesel only to the hybrid into PV, the battery with load following, and the best strategy; the split depends on that order. *Year 1 only (fast)* repeats year 1 over the project life, which saves most of the time of the two predictive runs.

### Design variants (`ui/src/lib/variants.js`, `ui/src/screens/variants/`)
A variant is the project with a few settings changed, kept by name in the project file (`variants`: id, name and the dotted paths it overrides, such as `bess.energy_kwh`). It holds only what it changes, so everything else follows the project, including later edits of the project. *Add a setting* offers every input of the PV module, mounting and losses, battery, wind, auxiliary loads, diesel, dispatch, fuel curve, energy management, cost and capital, debt, operating, currency and tax equity finance forms (limits and choices are those of the form); site, load and layout inputs are not offered, since the interface makes the load profile and the PV tables from them. Up to 8 variants.

*Compare variants* sends the project and every variant as one `batch` of the engine (the same command as the operating options and the tornado), so a variant whose settings the engine refuses, such as a negative capacity, shows its message instead of figures and the others are unaffected. *Year 1 only (fast)* simulates the first year and repeats it, as for the operating options. The table puts the designs side by side with the settings each variant changes (and the project's value), the best value of each row among the designs that meet the optimiser constraints highlighted (sizes are not ranked), and the net present cost and LCOE against the current design; a change below 0.5 % of the net present cost is within model accuracy. NPV and IRR are against diesel only, at the prices and costs of the same design. The comparison is not saved; it says when the project or a variant has changed since it was made.

### What drives the result (`ui/src/screens/sim/`)
The *What drives the result (tornado)* card simulates the current design once at a low and once at a high value of each listed input, one input at a time, in one batch with the base case. The sizes stay fixed; the sensitivity cases of the optimiser re-optimise them instead. Each input is a project path changed by a factor (× base), an amount added to the base (+ base, in percentage points for percentages) or a set value, and `load.kw` scales the load in every hour. The defaults are diesel price, fuel escalation, discount rate, PV and battery capex, battery replacement price and price decline, cycle life, calendar fade, PV degradation and availability, the irradiance (× 0.95 and 1.05 of the irradiance scale), genset O&M per run hour and the load. The wind speed scale can be added from the list. The bars start at the base value of the chosen result (NPV of savings, LCOE, IRR, equity IRR or fuel saved in year 1) and are sorted by swing. *Battery prices move together* lets the battery energy capex also move the power capex and the replacement price. Cycle life and calendar fade move the replacement year in whole-year steps, so their bars can be lumpy and asymmetric. A path the engine does not read, such as a typo or the module power and size (which only the layout and the equipment library use), is not simulated: its row shows *not an input of the engine* instead of a zero bar. The report shows the chart and table under Economics, and the workbook has a *Tornado* sheet with every result of every case.

### Optimiser (`engine/src/optimizer/`)
Every candidate is a full chronological lifecycle simulation, run multi-threaded.

| Algorithm | Use |
|---|---|
| **Grid + pattern search** | Exhaustive PV × BESS × C-rate grid (× genset count when the fleet is sized, × unit rating when it is searched), then Hooke-Jeeves refinement [30] at the best C-rate, genset count and rating. Gives the full search-space map. |
| **PSO** | Global-best particle swarm, inertia 0.9 → 0.4, c1 = c2 = 2 [31]. |
| **Hybrid SHO–QAO–GOA** | Spotted-hyena search, quadratic-approximation refinement and grasshopper diversification [32], with the equation corrections listed in `docs/LITERATURE.md`. |
| **MOPSO** | Pareto front of cost vs renewable fraction, SSSI, unmet load (LPSP) or CO2 [33], [48]. The reported "best" is the knee point, or the fuzzy best compromise [47] when chosen. |

All algorithms share these features:
- Constraints: maximum unmet load (in every simulated year, so load growth counts; of the site load, without a deferrable load), maximum unserved deferrable energy (with a deferrable load: its shortfall over its demand in every simulated year, a figure of its own that candidates report as `dl_unmet`; blank takes the unmet-load limit, so by default the pump must be served as reliably as the load), maximum loss-of-load hours and reserve shortfall hours per year (worst year, optional), maximum PV and wind ramp violations per year (with a ramp limit: steps in the worst year, a figure candidates report as `ramp_viol`; blank = no limit), minimum renewable fraction, maximum curtailment, land limit from the layout, capex budget, and minimum days of autonomy (optional, 0 = none). Metaheuristics handle them with a static penalty. With a critical share below 100 % the unmet-load and loss-of-load limits hold for the critical load (unserved critical energy ÷ critical load, hours with critical load unserved; candidates report these as `unmet` and `lole_h`), since the non-critical load may be shed.
- Days of autonomy: the usable energy of the battery (nameplate × starting state of health × SOC window × one-way efficiency, as the autonomy of the battery health card) must carry N days of the stated load, or of the year-1 mean load of the design (auxiliaries included) with none stated, with no PV, wind or gensets. A design without a battery has 0 days. With the constraint on, every candidate has `autonomy_d` and the best design a tile.
- Search variables: the grid tests the listed C-rates at the project's wind-turbine count. The metaheuristics search the C-rate continuously between the smallest and largest listed value, and the turbine count as an integer within its range.
- Genset fleet (optional, *Size the genset fleet*): the search also varies the number of gensets from *Genset units min* to *Genset units max* (both blank: the fleet's own count). 0 is allowed, so a diesel-free plant competes with the others. Each candidate runs with its own count: the dispatch commits only those units, the spinning reserve and N-1 check see only them, and the genset capex, O&M, starts and fuel follow from them. The grid search runs every count at every grid point, so it takes that many times longer; the metaheuristics search the count as an integer with the other sizes. With a mixed fleet only the main group (the first one) is sized and the further groups keep their units. The diesel-only reference for savings, IRR and payback stays the project's own fleet. Set a genset capex per kW on the Costs page, otherwise a smaller fleet only saves O&M; and keep an unmet-load, loss-of-load or reserve limit, since a fleet that is too small shows up only there. *Apply* sets the count of the main group.
- Genset unit rating (optional, *Genset unit rating*): the search also tries ratings per unit of the main group, as [43] picks units from a catalogue. *Search a list of ratings* takes the kW values typed; each runs with the project's minimum load, genset capex per kW, O&M per run hour and fuel curve, which is per kW and so scales with the rating. *Search the genset datasheets* takes every genset of the equipment library with a prime power, each with its own minimum load, fuel curve (from the litres per hour at 25 to 100 % load), price per kW as the genset capex and O&M per run hour, and the project's values where the datasheet has none. The grid search runs every rating at every grid point and genset count, so it takes that many times longer; the metaheuristics search the rating as an integer, the ratings sorted by kW. Combine it with the fleet sizing so the count follows the rating. Only the main group is sized, one rating for all its units; the further groups keep theirs, and the diesel-only reference keeps the project's fleet. The tiles, the ranked table, the system types table, the report and the workbook show the rating. *Apply* sets the rating of the main group, and with a datasheet selects it on the Equipment page and takes its minimum load, fuel curve, O&M per run hour and price.
- Repeated runs (optional, *Repeat runs*, metaheuristics only): a single run of a metaheuristic depends on its seed. With N runs each starts from its own seed derived from the random seed (the first is the seed itself, so one run gives what it always gave), as [47] and [48] repeat each method. The results list each run's seed, evaluations (positions evaluated: population × (iterations + 1) for PSO and MOPSO, population + iterations × (2 × population + 1) for the hybrid, which therefore spends about twice the evaluations for the same settings) and new simulations (sizes not met in an earlier run), and the best, mean and worst value with the sample standard deviation. The value is the objective of the run's best design, or for MOPSO the hypervolume of its front. The best design is the best of all runs; MOPSO reports the front of the run with the largest hypervolume. The convergence chart is that of the run reported. Runs are reproducible from the seed whatever the number of threads. Sensitivity cases and map cells that search again repeat the runs too, and report only their best. The workbook has a *Runs* sheet.
- Front statistics (MOPSO, optional, *Front quality and LPSP table*): the spacing of the front (the spread of each design's distance to its nearest neighbour, both objectives scaled 0 to 1; 0 is an evenly spread front and lower is better, which [48] reads the other way round) and its hypervolume (the share of the box from the best values to a reference point 10 % beyond the worst values on the fronts of all runs that the front dominates; higher is better), with the reference point stated in the results. The LPSP table, as in [48], gives for unmet-load targets of 0, 1, 2, 5 and 10 % the cheapest design of the front that meets each, with its sizes, fuel, CO2 and NPC; it is most useful with LPSP as the second objective and the max unmet load raised to 10 %, since the front holds only designs within that limit. With the genset fleet fixed the gensets cover the load, so cost and unmet load seldom trade off and the front may hold a single design; size the genset fleet as well. The workbook has an *LPSP targets* sheet.
- Best compromise (MOPSO): the knee point by default, the design closest to the ideal point with both objectives scaled 0 to 1; or the fuzzy best compromise of [47], which gives each objective a membership of 1 at its best value on the front and 0 at its worst and picks the design with the largest sum.
- Best design per system type (with genset sizing or a rating search on): for each combination of PV, battery, wind and gensets present or absent among the candidates the search simulated, the best feasible design by the objective, with how many designs of that type were simulated and how many met the constraints. It answers whether diesel is worth keeping at all, or what wind adds, without a separate run per system type. The table is also in the report and in the *System types* sheet of the Excel workbook.
- Sensitivity cases: diesel price, fuel escalation, discount rate, PV/BESS capex, load multiplier, battery life multiplier (cycle life × value, calendar fade ÷ value), cycle life, calendar fade, replacement price, battery price multiplier (energy and power capex and replacement price), replacement SOH, PV degradation, genset O&M per run hour, irradiance multiplier and wind speed multiplier. The two multipliers scale the project's irradiance and wind speed scales (above), and the PV or turbine output is computed again for each case; every other case reuses the PV and wind output of the main search. The end-of-life SOH is not offered: it also sets the fade per cycle, so the cycle part always reaches it after the rated cycle life.
- Two-way map (optional): two of the sensitivity variables and up to 10 values each. Each cell either runs the whole search again with both inputs set (*Run the whole search again*: the sizes follow the inputs, a 5 × 5 map takes about 25 searches) or simulates the best design of each system type found by the main search again with both inputs set and picks the cheapest that meets the constraints (*Simulate the best design of each system type again*: quick, but the sizes stay those of the main search). The results show the winning system type of each cell on a heat map coloured by its NPC, with a table; the report has both and the workbook a *Two-way map* sheet. On the example study a 5 × 5 map of diesel price and irradiance takes about 9 s searching again and 1 s simulating again, against 0.5 s for one search. The map runs in the optimisation job, so the progress bar and Cancel cover it; cells not reached after a cancel are left empty.

The metaheuristics also plot a convergence chart. All algorithms except MOPSO warn when the optimum sits on the search boundary.

### Electrical design (`engine/src/electrical/`)
The engine computes the design, auto-size, load flow, short-circuit and protection studies (`design.rs`, `loadflow.rs`, `fault.rs`, `protection.rs`) through one `electrical` command. The interface keeps only the drawings: the single-line diagram (`ui/src/lib/equip/sld.js`) and the time-current chart (`protection.js`). `engine/tests/electrical.rs` checks the engine against results the earlier JavaScript version wrote for twelve projects (`engine/tests/fixtures/electrical/`), to 1e-9 relative.

- String sizing:
  - Voc at the site minimum temperature against inverter and module voltage limits;
  - MPPT window from Vmp at the maximum cell temperature and at the site minimum. Vmp uses its own temperature coefficient: the datasheet value, or γPmax − αIsc when it is not given (slightly steeper than the true value, so conservative);
  - the maximum cell temperature is checked against the 99.9th percentile of the yield model's hourly cell temperature (hours above 200 W/m²), with a 5 °C margin for short peaks;
  - MPPT current check (1.25 × Isc).
- Transformers: chosen from datasheets. Loading, plus annual no-load and load losses integrated over the hourly flows.
- Cables:
  - current rating × derating × parallel runs, and voltage drop (DC: 2IRL/V; AC: √3 I (R cosφ + X sinφ) L / V) with R corrected to 70 °C;
  - I²R losses integrated over the hourly profiles, with distributed-load factors for MV collectors carrying several transformers;
  - auto-sizing picks the smallest cable and fewest runs that meet both limits.
- Cable lengths from the layout (`ui/src/lib/equip/siteplan.js`, `blocks.js`): with *Cable lengths from the layout map* ticked (the default) and the stations placed on the Site & layout map (*Plant* buttons over the map: PV stations, inverters, BESS and genset stations, the MV substation and the plant load; one substation only, placing it again moves it), the DC string cables, the AC cables of string inverters and the MV feeders are measured instead of typed:
  - *Inverters* in the design basis: *Central inverters in the PV stations* (the default) or *String inverters in the field*. With central inverters each PV station takes a block of tables; with string inverters each inverter pin takes a block, and its AC cable runs to a PV station. Blocks are balanced: every station or inverter takes the same number of tables, give or take one, nearest first, so no block collects twice its neighbour's power. *Auto-place* (over the map) puts the number of PV stations or inverters the design counts over the tables in compact blocks; drag them to adjust, Ctrl+Z undoes. *Blocks* colours the tables by the block they feed;
  - a string cable runs from the centre of each table to its PV station (central inverters) or its inverter (string inverters): the average length sets the losses and the cost, the longest run the voltage drop (shown as *longest* in the cable table, with a warning when it exceeds the limit, and met by auto-sizing). An inverter's AC cable runs to its PV station in the same way;
  - the *Inverter blocks* table lists each block: tables, kWp, string and AC runs, voltage drops on the longest runs, its share of the cable losses (by its cable lengths) and the loss as a share of its DC energy. The block that loses most is marked, and every block over a drop limit; a warning says when the map holds a different number of stations or inverters than the design;
  - a feeder runs from the stations of that kind to the substation: the average run sets the losses and the cost, the longest the voltage drop. So the BESS, genset and load feeders need their station placed, the PV feeder at least one PV station; a circuit with nothing placed keeps its typed length;
  - every distance is a straight line times the *Route factor* (1.25 to start, kept between 1 and 3), since trenches follow tracks, not the straight line;
  - the short LV runs inside a station stay typed. The stations are saved in the project file (`layout.stations`) and are part of undo; they are not written by *Export*.
- AC load flow: backward/forward sweep on the radial network for all 8,760 hours. It reports bus voltages, voltage deviation, network losses and limit violations.
- Reactive power at the grid connection: *Power factor at the grid connection* in the design basis (1 = none, the default). The MV main bus stands for the point of connection.
  - inverter and battery datasheets have a *Rated apparent power* (kVA). Blank or 0 takes the kW rating, so older libraries behave as before;
  - below 1 the design checks the PV inverters and the battery PCS on kVA: S ≥ √(P² + Q²) with Q = P tan φ at rated active power, P being the plant's AC rating (kWp ÷ the model's DC/AC ratio) for PV and the battery power for the PCS. IEEE 2800 [40] asks a reactive capability of at least 0.3287 × P, which is a power factor of 0.95. The *Reactive capability* table gives the kVA installed and needed, Q at rated P, the margin and the units needed, with a warning when the units fall short. Losses between the units and the connection are left out of this check;
  - the design does not add units by itself: the PV inverter count also sets the DC/AC ratio fed back to the model, so the choice between more units and a higher kVA rating is left to you;
  - in the load flow the reactive power drawn at the connection may be at most P tan φ: at export the plant supplies Q = P tan φ with its active power, at import it covers what the load and the network draw beyond that. The PV inverters (while they produce), the PCS and the running gensets share it by their spare kVA, √(S² − P²). The load flow reports the reactive energy they supply and the hours their spare kVA fell short. With 1 the load flow is the same as before.
- Weak-grid screening, with a utility short-circuit power set (*Short circuit and protection*):
  - short-circuit ratio SCR = utility short-circuit power ÷ the rated power of the PV inverters and battery PCS, with a warning below *Minimum short-circuit ratio* (3 for new projects; 0 = no check). IEEE 2800 sets no limit; below 3 a grid is usually called weak;
  - voltage dip on energising the largest transformer from the utility side: ΔU = m·Sn ÷ (S_sc + m·Sn), where m is half the first-peak inrush multiple (the fundamental of a half-sine current pulse). Transformer datasheets have an *Inrush current (first peak)*; 8 × rated is assumed when it is blank. Warned above *Max dip on energising a transformer* (5 % for new projects; 0 = no check);
  - both are screening estimates. The dip ignores the decay of the inrush over the following cycles and so errs high. A low ratio or a dip near the limit calls for a stability or switching study with the network operator.
- Islanded N-1 feeder screen after [49] (`screens.rs`), on by default (*Islanded N-1 screen*):
  - the network is a star at the MV bus, so each single outage leaves at most two islands. The outages are the utility incomer (with the grid connected), one PV feeder, the BESS feeder, one genset feeder (the largest group) and the load feeder; the first row has everything in service;
  - for the island that keeps the load: its grid-forming sources (the utility, the gensets, and the battery PCS when *Battery PCS forms the grid* says so; *Auto* takes yes off-grid and no with the grid connected), its firm capacity (the utility's import limit, the gensets, a grid-forming PCS and *PV counted as firm in an island*, 0 to start, of the PV AC rating, counted only with a grid-forming source there) and the load shed at the peak load, in all and for its critical share (*Critical share of the load*);
  - an island without a grid-forming source sheds all its load. A warning names each outage that leaves critical load unserved; the summary counts the outages that shed nothing and names the worst;
  - the load hangs on one feeder, so its own outage always sheds it whatever the sources. That row is shown, but kept out of the warnings and the summary; only a second feeder or a ring would avoid it;
  - the gensets are the main group (*Units* × *Unit rating*), as in the rest of the electrical design. The grid connection is the one of *Diesel & control*.
- Unbalanced-fault screen after [50] (`screens.rs`), with a utility short-circuit power and *Unbalanced fault: grid V+* above 0 (0.7 pu for new projects):
  - the utility is a Thevenin source behind Z = S_conv ÷ S_sc with its X/R, per unit on S_conv, the rated kVA of the PV inverters and PCS. Each sequence sees it alone;
  - the converters hold the grid-code droop on the positive sequence, Iq+ = K+ (0.9 − V+) below 0.9 pu (*Positive-sequence droop gain K+*, 2 to start; grid codes set it, often at least 1 to 2), and give the rest of the *Converter current limit* (1.1 pu) to the negative sequence, with |I+| + |I−| ≤ Imax so no phase exceeds the limit;
  - each sequence current carries an active part Id = (R/X)·Iq, which puts Z·I in phase with the voltage. Then |I| = (Z/X)·Iq and V+ = (X·Vg+ + 0.9·Z²·K+) ÷ (X + Z²·K+), V− = Vg− − Z·|I−|. [50] writes Id = −(R/X)·Iq; the sign follows its axis convention;
  - the negative sequence is cancelled (V− = 0, I− = Vg−/Z) when Vg− ≤ Z·(Imax − |I+|). The test in [50], Vg− ≤ Z·Imax, leaves out the positive-sequence current under the shared limit; it holds only when V+ stays above 0.9 pu. Otherwise all the current left goes to the negative sequence, which gives the lowest unbalance with K+ at its floor. A droop that asks for more than the limit takes all of it, and V− stays the grid's;
  - the screen reports V+, V−, the voltage unbalance factor V−/V+ (and Vg−/Vg+ without support), whether the negative sequence is cancelled and the current split. It gives no warning. A strong grid (small Z) leaves the plant little effect on the unbalance; a weak one lets it cancel it;
  - it relates to the reactive capability check as follows: that check is steady state, on kVA at rated active power and the power factor asked; in a fault the converters are limited by current, which this screen shares between the sequences. Both use the same kVA ratings.
- Feedback to the model: DC wiring loss (as a constant annual fraction), AC loss and BESS path efficiency (cables and transformer load loss), DC/AC ratio, built kWp, and the no-load loss of the PV and BESS step-up transformers as auxiliary loads, each counted only with its own asset.
- Short-circuit currents (`fault.rs`), IEC 60909-0 [34] equivalent voltage source c·Un/√3 at the fault, at every bus of the radial network (MV bus, PV feeder end, PV transformer LV, inverter terminals, BESS transformer LV and PCS terminals, genset transformer LV and terminals, load feeder end and load LV bus):
  - sources: gensets behind X″d (R = 0.15 X″d at LV, 0.07 X″d at MV) with K_G; the utility network from its short-circuit power and X/R (*Utility short-circuit power*, 0 for an isolated plant); PV inverters and battery PCS as current sources at their *fault current contribution* (× rated, 1.2 when blank), added by magnitude;
  - branches: transformers from impedance and load loss (or the datasheet X/R) with K_T, cables at 20 °C;
  - maximum: every genset, the battery and full PV, c = 1.10 MV / 1.05 LV. Minimum: the *units always online*, the battery and no PV, c = 1.00 / 0.95, cables at 80 °C, no correction factors;
  - for each fault the tree is re-rooted at the fault bus; the admittance of each node towards the sources gives Ik″, the share of every source and the current of every branch, which the protection uses;
  - peak ip = κ √2 Ik″ with κ by method B (1.15 κ, at most 1.8 LV / 2.0 MV), converters √2 Ik″; breaking current Ib with the genset decay μ at 0.1 s; line-to-earth Ik1 from the sequence networks in series (Z2 = Z1, inverters drive the positive sequence only);
  - zero sequence from the vector groups: an earthed star facing a delta (Dyn) earths its own side, YNyn passes it through, a Dy LV side is an IT system (no first-fault current); MV earthing by neutral resistor (its current limit), solid (Z0 = Z1 at the bus) or isolated; cable Z0 = 3 Z1; genset neutrals not earthed; no motor contribution from the load.
- Protection (`protection.rs`): one overcurrent device per main breaker (load, PV, BESS and genset feeders of the MV switchboard, utility incomer, PV transformer LV incomer, PCS and genset breakers):
  - inverse-time curves of IEC 60255-151 [35] (standard, very, extremely and long-time inverse), flat beyond 20 × pickup, with an optional instantaneous stage (50 ms);
  - suggested settings: pickup 1.25 × full-load current, rounded up to a step; time multiplier from the downstream devices up, the smallest 0.025 step that keeps the *grading margin* (0.3 s) at the fault current each device carries; an instantaneous stage on PV and BESS transformer feeders (and the load feeder with a load transformer) at 1.3 × the LV through-fault, only when it stays below the MV-end fault. Any value can be typed over in the device table; blank returns to the suggestion;
  - grading checks: a load-feeder fault (load feeder against each source feeder and the incomer), an MV bus fault (genset feeder against the genset breaker), an inverter-cable fault (PV LV incomer against the PV feeder) and a PCS-cable fault (PCS breaker against the BESS feeder). A device whose current stays below pickup does not trip and needs no margin;
  - checks: pickup against full-load current and the cable rating, sensitivity (two-phase fault at the end of the device's zone in the minimum case at least 1.5 × pickup; gensets point to voltage-restrained overcurrent), the breaker's rated current, voltage, breaking capacity (Ib for MV, Ik″ for LV), making capacity (ip) and short-time withstand (I²t of the thermal equivalent current over the clearing time);
  - breakers: a new *Circuit breakers* datasheet type (rated voltage and current, breaking and making capacity, short-time withstand); *Auto* picks the smallest one that carries the current and meets the duty;
  - cable short-time withstand: adiabatic k·S/√t (XLPE, k = 143 copper, 94 aluminium) against the thermal equivalent current at the larger end fault, for the clearing time of its device (*Clearing time without overcurrent trip* when the device does not see the fault), with the cross-section needed;
  - time-current chart: log-log, currents referred to the MV voltage, the MV bus fault level and the operating points of the grading checks.
- Single-line diagram: A3 drawing with IEC-style symbols, protection tags, cable labels, the maximum fault levels at the buses, notes, legend and title block. Exports to SVG/PNG and is embedded in the report.
- The report shows the reactive capability, the grid strength, the unbalanced fault and the islanded N-1 screen when they apply, the fault levels, the protection settings, the grading and cable checks and the time-current chart; the workbook has a *Protection* sheet with the same tables and the curve points.

### Project finance (`engine/src/finance/`)
The financial model is an annual after-tax cash flow:
- Ownership structures: host-owned, single-owner PPA, third-party lease/PPA with the host's savings view, and a partnership flip between a tax equity investor and a sponsor (cash and tax shares before and after the flip, a flip at the investor's target IRR or a fixed year, investment and production tax credits).
- Costs: construction period with IDC, soft costs and VAT.
- Debt: sized by gearing and/or DSCR sculpting, optionally on revenue cut to P90 (the factor can come from the inter-annual variability run); sculpted, annuity or equal-principal repayment; DSRA. Debt service can be paid semi-annually, quarterly or monthly inside the yearly model, with sizing, sculpting, cover and reserve per period, a seasonal spread of the cash flow and interest during construction on a drawdown schedule.
- Currency: the loan, the tariff or both in another currency, on a flat, escalating or yearly exchange rate path; the realised exchange loss is deductible, and the results show the returns with the rate 20 % lower to 30 % higher.
- Tax: depreciation by asset class (including Indonesian groups), loss carry-forward, tax holiday, creditable withholding and the Art. 31E reduced rate.
- Revenue: take-or-pay and deemed energy; multi-component staged tariffs (PLN A/B/E/F style); a tariff solver for a target IRR.

`docs/FINANCE.md` gives every formula, the presets, and lessons from two industry financial models: what was adopted, and the spreadsheet errors that were avoided.

## Why Rust (and not Julia)
- Speed: the sizing search runs hundreds to thousands of 8760 h × 25-year simulations. With rule-based dispatch the engine runs about 150 full 25-year simulations per CPU-second on the example project. The predictive EMS, which re-plans every hour, runs about one.
- One small native program with no runtime, package installs or JIT start-up delay; the engine and the window shell are one Rust program.
- The interface is a web page shown in a native window with the system's web engine (Tauri), so maps (Leaflet / Google tiles) and interactive charts (Plotly) work the same on every OS without bundling a browser.
- Version 1 had its engine in C++17; version 2 ports it to Rust with the same results to within rounding (`docs/VALIDATION.md`).
- Julia (JuMP) would suit LP/MILP formulations; the DP-based EMS and grid search here need no solver.

## Layout map tools

The Site & layout page has one card for the map. The bar on top holds the place search, the switch between **Map**, **3D**
and **Google Maps**, the base map, **Undo**, **Redo**, the **⋯** menu and full screen. The drawing tools run down the left.
Whatever you select shows up in the inspector on the right, so there are no popups over the map any more. Click an item on
the map or in the 3D view to open it there; the **×** at its corner, or Esc in the 3D view, closes it.

Moving the site more than a kilometre (search, coordinates or the marker) asks whether to move the layout with it. Every
item, table and station then keeps its east and north distance from the site, so the drawing arrives as it was. Items left
more than 50 km from the site stop the PV yield; the map frames only what is near the site and says how many are far away.

A PV area raised above the ground (drawn on a roof, or traced from one) keeps at most 1 m from its edge instead of the edge
setback of a field. Where no full table fits on it, each row takes the longest table that fits at each place, down to one
module, and the layout counts the modules table by table. A traced roof runs its rows along its longest edge; for an area
drawn by hand, *Square to the longest side* does the same. Buildings in the 3D view are plain walls and roofs.

### Drawing

- **PV area** draws a PV area on the ground. Click its corners and double-click (or click the first corner) to finish. The
  tables fill it at once while *auto-update* is on.
- **Rooftop** puts panels on a building. Turn it on and click a building you've drawn (or loaded from OpenStreetMap). On a
  flat roof you get one PV area at the roof height with the project's rows. On a pitched roof you get one PV area per roof
  plane that faces within 100° of the equator, flush with the plane: tilt and ground slope both equal the pitch, and the
  table centre sits 0.15 m over the roof. Each area keeps 0.5 m from the roof edges. The building stays where it is, so it
  still shades whatever is around it. Set the roof shape on the building first (see Buildings below).
- **Carport** draws a carport canopy. It's a PV area marked as a carport: one plane of tables (a canopy), 5° tilt facing the
  equator, the table centre 3 m up, and no edge setback, so the panels run to the outline you drew. The 3D view adds the
  posts, the beams and a few parked cars. Change the height in the inspector (*Canopy height*), or drag it up or down in 3D.
- **Building** draws a building footprint, then opens it so you can set its height and roof.
- **Tree** places a tree with every click until you press it again or Esc. New trees get a round crown.
- **Keep out** draws a zone the tables keep out of. **Path** draws a road or walkway as a line, then a strip of the width
  you give it (4 m to start) that the tables keep off.

Placed shapes stay editable on the map: double-click one (or use *Move corners* in the inspector) and drag its corners, or
use *Move shape* (*Move* for a tree) and drag it whole. A click on the map or Esc ends it. Each change is saved and the tables
are laid out again. You can't edit a path's route: remove it and draw it again. Dragging a corner of a path, or turning it,
makes it an ordinary keep-out zone.

### Buildings

- **Height**: on a flat roof, the roof. On a pitched roof, the eaves (the top of the walls). The ridge comes from the pitch.
- **Roof**: *Flat*, *Gable* (two planes meeting at a ridge), *Hip* (four planes; the short ends slope too) or *Shed* (one
  plane). Picking a pitched roof sets the ridge along the building's longest side, or for a shed, falling towards the
  equator. Change it with *Ridge runs towards* (*Falls towards* for a shed), an azimuth from north.
- **Pitch**: 1 to 75°, 25° to start.
- The roof works on any footprint. It's built from the footprint's extent along and across the ridge direction, so on an
  L-shaped or odd building the ridge sits on the middle of the whole outline. Square up odd outlines first if you need an
  exact roof.
- **Panels on this roof** does the same as the Rooftop tool, for the building that's open.
- The length, width and rotation fields show only for four-cornered footprints with square corners.

### Trees

- **Shape**: *Round crown*, *Cone (pine)*, *Palm*, or *Column*. Column is how every tree was drawn and shaded before, so

  the same for every shape.

- **Surface height above ground**: 0 for the ground, the roof height for a flat roof.

  a carport canopy or a raised array next to a ground array.

### Tables, plant and files

- **Take out** (left, under Tables) lets you click tables to take them out of the layout, and click a dashed outline to put
  one back. **Put all back** puts every one back. Tables you took out stay out when the layout is made again, as long as the
  grid stays close: a new table whose centre is within about half a table of a removed one is left out. Layouts over 30 000
  tables can't be edited this way.
- **Stations** (left, under Plant) opens the PV station, Inverter, BESS station, Genset hall, MV substation and Plant load
  markers, **Auto-place inverters** and **Colour tables by block**. They work as before (see Electrical design).
- The **⋯** menu holds what you need now and then: *Import KML, KMZ or GeoJSON* (choose what the shapes become just below
  it), *Export the layout* (GeoJSON or KML), *Own drone or survey image*, *Trace a roof on your image*, *Buildings from
  OpenStreetMap* and *Clear all items*.
- **Undo** and **Redo** (Ctrl+Z and Ctrl+Shift+Z or Ctrl+Y, Cmd on a Mac) step through up to 100 changes to the drawn items,
  the removed tables and the plant's stations. A drag in the 3D view is one step. Layout parameters aren't part of it.
- *Buildings from OpenStreetMap* loads the outlines of the map view (up to 4 km²) through the public Overpass API [37], with their
  height from the height tag or 3 m per storey (6 m when neither is given). A click on one uses it as a rooftop PV area, a
  building or a keep-out zone; the bar above the map adds them all as buildings, or those inside PV areas as keep-out zones.
  One request runs at a time, the results are kept for the session and a busy server gets 30 s of rest.
- *Keep tables clear by* (in the inspector of a keep-out zone, path, building or tree) keeps the tables at least that far
  from it. Blank means no clearance.
- *Access aisle after every … rows* and *Access aisle width* (Layout parameters) leave a strip after each set of rows in
  every PV area, for maintenance roads. For a road across the rows, draw a path.
- *Assisted roof layout*: Ctrl+click a roof (Cmd+click on a Mac) to make it a PV area. The outline is the building drawn
  there, else a trace of your own image where it covers the click, else the OpenStreetMap building there. This older route
  replaces the building with the PV area, so its shade on other tables is gone too. For most roofs the Rooftop tool is the
  better choice now: it keeps the building and follows a pitched roof.
- *Own image…* loads your own drone or survey orthophoto (PNG, JPEG or WebP) with its world file (.pgw, .jgw, .wld; a GeoTIFF converts with `gdal_translate -of JPEG -co WORLDFILE=YES ortho.tif ortho.jpg`) and, if you have it, its .prj. Coordinates in UTM (WGS 84, any zone, north or south), Web Mercator or longitude and latitude are read from the .prj; without one, the program takes the one of these systems that puts the image within 50 km of the site. A .prj naming any other system is refused: export the image in one of these. The line under the map shows the file, its ground resolution and coordinate system, sets the opacity and removes the image. Transparent pixels count as outside the image. The image is resampled onto the map's pixel grid (at most 4096 pixels a side) and is not saved with the project. *Trace roof* reads only this image, since the terms of Esri and Google do not allow outlines to be derived from their imagery: a click on a roof grows a region from the click over pixels of the roof's colour (CIELAB distance plus half the colour change across about a metre, on an image smoothed over about half a metre), at the threshold where the region is most stable [38], stepping out one zoom level while it reaches the edge of the window (a roof that runs off the image is reported instead of traced); gaps of about half a metre close and necks of about 2 m are cut; the edge is then set where the colour changes, each pixel within a metre of it going to the side (roof or surroundings) whose local mean colour is nearer its own; openings of 4 m² or more stay as holes. The outline is simplified (Douglas-Peucker [39]), then taken as its smallest rectangle when it fills 90 % of it, or squared to the roof's main directions. On synthetic test images (roofs of 450 to 1800 m² at 5 to 20 cm per pixel, one of them of low contrast) the corners come out within about two pixels: 0.12 m at 5 cm and 0.47 m at 20 cm per pixel. The faces of a pitched roof that differ little in shade can come out as one outline, and a rooftop unit close to the roof's colour as part of the roof; check the result against the image and split or redraw where needed.
- *Import* reads KML, KMZ (the KML inside, unpacked by the system's decompression) and GeoJSON: polygons become the kind chosen next to the button, holes exclusion zones, points trees; files written by *Export* keep every kind and field. *Export* writes the areas, buildings, trees and tables as GeoJSON or KML.
- *GCR for shade-free rows* sets the ground coverage ratio at which fixed rows keep clear of each other's shadow between the chosen solar hours on the winter solstice, rounded down to 0.01.

## 3D view

Pick **3D** in the bar on top. The app draws the view on your graphics card: Metal on a Mac, Direct3D 12 on Windows,
Vulkan on Linux. The chip in the bar at the bottom says which. If the computer has no graphics card the app can use, the
view falls back to a slower drawing on the page itself, without the cell detail and the mounting structures.

What you see:

- **Tables** with their modules and cells (the cells show once you zoom in close enough), on their mounting structures:
  front and rear posts every 3.5 m along a fixed table, the rafter between them and two rails under the modules; one post
  per position and a torque tube for trackers. On very large plants (over 6000 tables) only the end posts are drawn.
  Seen from behind, a table shows its grey backsheet.
- **Buildings** with their roofs, windows on each floor of the long walls and a door. On a pitched roof the end walls go up
  to the ridge. Rooftop panels sit flush on their roof plane.
- **Trees** by shape. A round crown is a few clusters of leaves, a cone is three tiers, a palm has a curved trunk and
  drooping fronds. Each crown is drawn inside the shape the yield calculation shades with, so what you see is never bigger
  than what's counted.
- **Carports** with their posts, beams and some parked cars, the plant's stations and inverters as boxes, and, if you tick
  them under *View*, the cable routes.
- **Shadows** from the sun on the 21st of the chosen month at the chosen solar hour. They fall on the ground, on roofs and on
  the panels themselves. **▶** plays the day from 5:00 to 19:00.
- **The satellite map underneath.** With *Map underneath* ticked under *View* (on by default), the ground is the satellite
  image of the site, so the tables, buildings, trees and carports stand on the real place and their shadows fall on it.
  PV areas on the ground show as outlines so the image stays in view. The image covers a square round the layout, at
  most 6.4 km a side, and is fetched once for it, so small edits don't fetch it again. Without internet the view draws
  the plain ground and *View* says so. The credit for the imagery shows in the top right corner.

Moving around:

- Drag to turn the view, shift-drag or drag with the right button to pan, and use the wheel (or + and -) to zoom. The arrow
  keys turn it too. **Reset view** brings back the whole site.
- The small E, N and Up arrows in the bottom corner show which way is east, north and up.
- *View* in the bottom bar sets the table colours (one colour, by inverter block, or by shade from the last yield
  calculation) and shows or hides the mounting structures, the cable routes and the satellite map underneath.

Editing in 3D:

- Click an item to select it: an area (or any of its tables), a building, a tree or a carport. A dashed box shows what you
  picked and the inspector opens it. Click a table and the top right also shows its inverter block, the block's average
  string cable, its loss and voltage drop, and the table's shade.
- **Move** (W) shows arrows east, north and, for PV areas and carports, up. Buildings and trees stay on the ground.
  Moving a PV area up changes its surface height; moving a carport up changes its canopy height.
- **Turn** (E) shows a ring about the vertical for every item. Turning a building turns its ridge with it. Turning a PV
  area gives it its own azimuth (the project's plus the turn), so its rows turn too. A PV area on the ground also gets
  rings about the east and north axes: these tilt its ground, and they set the same *Ground slope* and *Falls towards* you
  can type in the inspector (up to 45°). Rooftop areas, carports and trackers don't get these rings.
- **Size** (R) shows square handles along the item's long side, across it and up. For a building that's length, width and
  eave height; for a tree, crown diameter (either flat handle) and height; for a PV area or carport, its length, width
  and table height.
- **snap** steps moves and sizes by 0.5 m, turns by 5° and ground tilts by 1°. Untick it for free values.
- While you drag, the view shows the item where it's going. A PV area's tables are left out until you let go, then the
  area is filled again. Each drag is one undo step. Esc while dragging puts the item back; Esc otherwise clears the
  selection.

## How the shading sees buildings, roofs, trees and slopes

The yield uses the same shapes as the 3D view. The near shading works out, for about 20 000 points spread over the tables,
the height of the skyline in every 2° of azimuth (the "near horizon"), and the sun is blocked at a point when it's lower
than that skyline. This is what changed with the 3D work:

- **Pitched roofs.** A roof is the lowest of its planes over the footprint: two for a gable, four for a hip, one for a shed.
  Along a line of sight the roof height then changes in straight pieces, so the highest point of the skyline is always at
  a wall or where two planes meet (the ridge or a hip line). The shading looks at exactly those points, so it's exact for
  the shape, not sampled. A point inside the footprint counts as under the roof only when it's below the roof there. Panels
  on the roof are above it, so they see the rest of the roof normally: a point on the far side of a ridge is shaded by
  the ridge when the sun is low behind it.
- **Tree crowns.** A round crown is half an ellipsoid whose top is the tree height and whose sides come down by the crown
  radius (at most half the height). A cone narrows straight from the crown at 16 % of the height up to its tip. A palm's
  fronds droop by half the distance from the trunk. The crown height along a line of sight is curved for these, so it's
  sampled at 25 points across the crown. Against a fine brute-force scan the result is within 0.5°. A column is the
  old flat-topped cylinder.
- **Sloped ground.** Each table now sits on the ground at its centre, as the 3D view draws it, and the shade points are
  raised or lowered with it. Before, the yield ignored the slope height entirely, so a table downhill of a building saw it
  as if both stood on the same level. Tables are rigid, so the whole table moves by the ground height at its centre.
- **Table height per area.** An area's *Table centre over the surface* sets the height of its shade points. The row-to-row
  view of the ground for bifacial modules still uses the project's table height.

Projects saved before this keep their results to the last digit, with one exception. Flat buildings and column trees take
the same code path as before, and a roof, a crown shape or a table height only counts once you set it. The exception is the
slope fix: a project with a sloped PV area and buildings or trees nearby will see its near shading change, because the old
numbers left the slope out. That change is a correction, not a new setting.

- *Sun path and horizon* plots the sun on the 21st of each month in solar time over the terrain horizon (PV page) and the near horizon of the objects as the tables see it.

## Limitations / next steps
- The genset rating search gives every unit of the main group one rating; a fleet of mixed ratings comes only from genset groups set by hand. A rating from a typed list keeps the project's fuel curve per kW, so a small engine is taken as efficient as a large one at the same loading; use datasheets where that matters. The hypervolume is scaled over the fronts of one optimisation, so it compares the runs of that optimisation, not separate optimisations. The algorithms are not given equal evaluation budgets; the results state each run's evaluations instead.
- The optimiser does not size the PV inverter (DC/AC ratio). The cost data cannot support it: the PV capex is one price per kWp DC that includes the inverters, and only the inverter replacement has a price per kW AC, so a smaller inverter would cut only the replacement while its clipping loss counts in full, and the search would favour high ratios for the wrong reason. Doing it properly needs a separate inverter capex per kW AC and the PV profile before clipping for every candidate ratio. Size the ratio on the PV page and compare a few values as design variants.
- Protection covers phase overcurrent of the main breakers. Earth-fault, differential, directional and voltage-restrained settings, arc-flash energy and fuse curves are not computed; LV trip units are drawn with the IEC relay curves.
- The islanded N-1 screen compares firm capacity with the peak load. It runs no islanded load flow: frequency as an unknown, droop sharing, voltage- and frequency-dependent loads and voltage limits in the island [49] are not modelled, nor battery energy, genset loading limits or the genset groups of a mixed fleet. The unbalanced-fault screen takes one Thevenin source and one aggregated converter, with the grid voltages during the fault as inputs; the plant's own cables and transformers, zero sequence and the fault's dynamics are left out.
- The hydrogen chain from the Chad paper (electrolyser, tank, fuel cell) is not modelled.
- Grid charging under load following and cycle charging follows fixed rules (fill before a scheduled outage, charge in hours where the spread over the next 23 hours pays); it is not an optimum, and random outages are not foreseen. The predictive EMS weighs grid charging hour by hour. The frequency reserve is held, not called: the energy that regulation moves in and out of the battery, and any payment for it, are not modelled, and the reserve is symmetric (the same power up and down).
- No frequency or voltage dynamics below the time step (15 minutes at the shortest): spinning reserve and the N-1 check stand in for them. PV, wind and weather stay hourly data filled into shorter steps; only the load keeps a finer resolution.
- The PV and wind ramp limit works on hourly data filled into 15 or 30 minute steps, which hold no cloud ramps: its violations, battery work and curtailment are a lower bound, and a real ramp study needs minute data. The battery does not discharge into the grid to smooth a fall in export, so with a grid connection a fall in export is neither met nor counted. The battery's own dispatch (load following, cycle charging, the EMS plan) is not ramp limited, and the predictive plan does not see the limit.
- Diffuse row shading and the rear side of bifacial modules take the rows as a long array of identical rows on flat ground (2-D), with the first and last rows open on one side. Light passing between the modules and the uneven rear irradiance along the slant are not modelled; enter the rear mismatch in the rear-side loss. Sloped ground counts only across the rows of fixed tables (trackers have their own cross slope), near shading takes a sloped area as level, and the plain ground reflection without diffuse row shading takes level ground. Spectral effects of precipitable water and aerosols beyond what the clear-sky index carries are not modelled.
- With PV areas of their own orientation, the tilt scan varies the tables at the project's orientation (areas with their own tilt keep it, and near shading keeps the table heights of the project's tilt), and the PVGIS cross-check and *GCR for shade-free rows* use the project's orientation. A layout whose near shading would take minutes (points on the tables times object corners over 10⁹) is refused with a message; simplify the outlines or remove distant objects.
- Near shading resolves the strings only as finely as the points on the tables (about 20 000 in all), and a sun behind two crowns passes only the higher one's leaves; objects shade neither the ground between the rows nor the rear side of bifacial modules. Areas with their own orientation share the project's row geometry (GCR, table width and height).
- A canopy takes the project's cooling choice (PV page; set 20 W/m²K for a closed back), gets rear-side light only with edge rows on (its back then sees the ground of one open row, with more canopies at the project's GCR in front of it), and leaves only the gap between tables along its rows. A Y-frame is two canopy areas facing opposite ways.
- Battery ageing by depth of discharge counts cycles at the time step, so cycles shorter than a step are not seen, and Miner's rule adds the damage of each cycle whatever its order, C-rate, mean SOC or temperature. The curve's points are datasheet values at the datasheet's test conditions. The predictive plan prices wear at one depth (the SOC window), not cycle by cycle.
- Minimum up and down times treat the units as alike and are held in real time only; the predictive plan sees the start cost, not the times. A unit is the same unit from one year to the next.
- Genset wear spreads a group's run hours evenly over its units, so they reach an overhaul or their life together; a fleet run lead-lag wears its lead unit sooner. Units start at 0 h, overhaul and replacement prices do not escalate, and an overhaul restores no value in the salvage. The dispatch and the optimiser's merit order do not weigh wear when they commit units.
- The deferrable load in water uses one energy per m³: a pump that moves less water per kWh at part power (flow as a power of the input power) or at a falling well level is not modelled, since the store would then have to be kept in water and the dispatch would trade part-load efficiency against surplus. The store has no losses and no minimum level, the day's energy is drawn at the window's end in the accounting (not spread over the day as water is used), and the predictive EMS schedules the load by a rule before it plans the battery rather than in one optimisation. The day-ahead schedule does not plan it yet.
- The critical share is one fraction of the site load for every hour; a critical load with its own profile, or more than two priorities, is not modelled. The rule-based dispatch does not choose which load to serve: the split is an attribution of each step's shortfall, and only the predictive EMS and critical-only supply act on it.
- The outage survival study runs in hourly steps over year 1 with a simple outage dispatch (no planner, spinning reserve or ramp limits), takes the units still working at each hour as working from the start (slightly low with a battery), does not repair units within an outage, gives every unit the same failure model, leaves PCS outages out and has no fuel limit.
- Emission factors are fixed per litre. The rise of NOx and PM2.5 per litre at low loading and with engine size, which [43] models, is not modelled: it needs engine-specific data a planner seldom has, and the fuel curve already charges part-load running with more litres.
- The comparison with metered PV output fits one soiling (constant or by month) and one availability. It sees outages only where the meter falls to zero in good sun, compares the year-1 model with the meter's year, and does not separate soiling from other steady losses or from curtailment by the plant's control.
- The example's site coordinates (−2.5°, 115.5°) are a placeholder; set the real plant location before using the results.
